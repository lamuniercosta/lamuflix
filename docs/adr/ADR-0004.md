# ADR-0004. Enrichment messaging topology: quorum queues, TTL retry queue, dead-letter queue and sweeper design

- Status: Accepted
- Date: 2026-09-30
- Ticket: DEV-18 (parent DEV-283)

## Context

Three Core handlers enqueue enrichment work through the `IEnrichmentQueue` port: `RequestEnrichmentCommandHandler`, `RequeueStrandedMoviesCommandHandler` and `ImportMovieFolderCommandHandler`. The built solution has no implementation of that port and nothing consumes the queue. The RabbitMQ code that exists lives in projects that DEV-19 retired from the solution. That code:

- uses `RabbitMQ.Client` 6.x and its synchronous model;
- opens a connection per publish;
- reads the queue names `task_queue` and `task_queue_dlq` from raw configuration;
- has no publisher confirms, no retry delay and no trace propagation.

Enrichment calls an external metadata provider, so it can fail. Some failures are transient: the provider is unavailable, or it rate-limits us. Others are terminal. Core already makes that decision. `EnrichmentFailureClassifier` maps an exception to a failure category, and the attempt policy turns the category and attempt into `Retry`, `RetryDelayed` or `DeadLetter` (ADR-0006, ADR-0017). The transport must carry that decision out without losing work, without looping forever, and without making a second decision of its own.

A movie is claimed before enrichment. `IMovieRepository.TryClaimForEnrichmentAsync` succeeds only for a `Pending` movie whose last attempt is older than `EnrichmentOptions.ClaimLease`. A successful claim stamps the attempt time and increments the attempt count. There is no release operation.

`RabbitMQ.Client` 7 replaces `IModel` with `IChannel`, makes the API asynchronous end to end, and adds built-in publisher confirmation tracking (`publisherConfirmationsEnabled`, `publisherConfirmationTrackingEnabled`).

## Decision

### Topology

One durable direct exchange, `lamuflix.enrichment`, and three durable quorum queues. One `RabbitMqTopology` owner declares them, idempotently. The publisher awaits it on first use, and the consumer awaits it at startup.

| Queue | Routing key | Arguments |
|---|---|---|
| `enrichment.requested` | `requested` | dead-letters to `lamuflix.enrichment` with key `dead-letter`; `x-delivery-limit` = `EnrichmentOptions.MaxAttempts`; at-least-once dead-lettering; `x-overflow` = `reject-publish` |
| `enrichment.retry` | `retry` | `x-message-ttl` = `RabbitMqOptions.RetryDelay` in whole milliseconds; dead-letters to `lamuflix.enrichment` with key `requested`; at-least-once dead-lettering; `x-overflow` = `reject-publish` |
| `enrichment.dead-letter` | `dead-letter` | none; no automatic retry |

The delivery limit on `enrichment.requested` protects against a crash loop on one broker message. It is not the application's attempt counter. That counter is `EnrichmentRequested.Attempt` on the wire, and each republish carries the next value decided by Core.

Quorum at-least-once dead-lettering needs a dead-letter exchange, `reject-publish` overflow and the broker's `stream_queue` feature flag. The integration tests declare and assert the topology against the pinned `rabbitmq:4.0.0` image.

### Publishing

- There is one process-owned `IConnection`, created lazily and asynchronously. A failed creation surfaces to the caller and is not cached, so a later call can try again. The owner handles shutdown and disposal.
- Each publish opens its own channel with confirmation tracking enabled and disposes it afterwards. No channel is shared between concurrent publishes.
- Messages are persistent and `mandatory`. A nack, a returned (unroutable) message or a connection failure is an exception from `EnqueueAsync`. A confirm alone does not prove routing. The mandatory flag and the returned-message handling close that gap.

### Consuming and retry

The consumer is an `AsyncEventingBasicConsumer` with manual acknowledgement, and prefetch comes from `RabbitMqOptions.Prefetch`. It carries transport only.

For each message it opens a DI scope and dispatches `ProcessEnrichmentCommand` to the Core `ProcessEnrichmentCommandHandler` through the usual decorator pipeline (Tracing, then Logging, then Validation, then the handler). The handler:

1. claims the movie;
2. calls the metadata provider;
3. applies the result, or classifies the failure and applies the one Core attempt policy (`EnrichmentRetryPolicy`).

The consumer maps the outcome to a routing key:

| Outcome | Transport action |
|---|---|
| Completed | ack |
| Skipped (claim refused) | ack, logged and tagged as skipped, never as enriched |
| `Retry` or `RetryDelayed` | republish to `retry` with the next attempt, then ack |
| `DeadLetter` | the movie is marked Failed; republish to `dead-letter`, then ack |
| Body cannot be read | `nack` with `requeue: false`, so it reaches `enrichment.dead-letter` through the dead-letter exchange |
| Host stopping | `nack` with `requeue: true`; the movie is not marked Failed |

A republish uses the same confirmed, mandatory publish path as the initial enqueue. The original is acked only after the republish is confirmed and routed. After a failed or uncertain republish, or any exception, the message is never acked as a success.

Both retry kinds go through the TTL queue. A retry that arrived before the claim lease expired would be refused and acked, and the retry would be lost. So when the consumer is active, startup validation requires that `EnrichmentOptions.ClaimLease` is explicitly set and positive, and that the integer-millisecond TTL is strictly greater than it. It compares the converted value, so rounding cannot erase the margin. No lease default is invented and neither value is adjusted. Exponential backoff is not part of this design: the delay is one fixed value.

### Trace propagation

`Propagators.DefaultTextMapPropagator` is set to the OpenTelemetry API's W3C `TraceContextPropagator` when the messaging services are registered. The publisher starts a producer span, `Enrichment.Enqueue`, from the `LamuFlix` activity source and injects `traceparent`, and `tracestate` only when one exists, into the message headers.

Nothing is listening when no OpenTelemetry SDK or listener is registered, and then `StartActivity` returns null. In that case the publisher still injects a valid context: the ambient one if there is one, otherwise a new one. The consumer extracts the context and starts a consumer span, `Enrichment.Process`, parented to it. On a redelivery it adds an `ActivityLink` to the earlier context.

Only `OpenTelemetry.Api` is referenced, and only from Infrastructure. There is no SDK, exporter or instrumentation package. Core references neither RabbitMQ nor OpenTelemetry.

### Activation boundary

The connection owner, topology, publisher and the broker readiness health check are always registered. The consumer and the processing handler are registered only when both an `IMetadataProvider` and an `IMovieRepository` are registered.

Neither port has a production implementation yet. The metadata provider is DEV-303, and the repository and DbContext wiring is DEV-392. Until both land, the Api starts, logs once that the consumer is inactive, and leaves messages durably in `enrichment.requested`. No stub provider or repository is installed. `ValidateOnBuild` and `ValidateScopes` stay enabled.

### Readiness

The broker contributes one health check, tagged `ready`, over the shared connection owner. It reports Unhealthy when the broker cannot be reached, and it never publishes, consumes or exposes credentials.

The application's `/health/live` and `/health/ready` routes do not exist yet. Mapping them is a separate follow-up. Until that lands, the check is registered but not reachable over HTTP.

### Stranded work: the sweeper (design only)

DEV-18 **records** the sweeper design and does **not** implement it.

A `StrandedMovieSweeper` runs periodically, every `EnrichmentOptions.SweepInterval`. It finds `Pending` movies whose last attempt (`MovieRecord.LastAttemptAt`) is older than the claim lease, and movies left `Pending` with no queued message. It re-enqueues `EnrichmentRequested` for each one through `RequeueStrandedMoviesCommandHandler`, without claiming. It uses the existing `Status`, `LastAttemptAt` and `EnrichmentAttempts` columns and needs no schema change.

How the sweeper hands a claim off is still an open owner decision (DEV-299 Q1, DEV-316), and this ADR does not settle it.

## Consequences

- Enqueued work is durable once `EnqueueAsync` returns, and a publish that was not stored and routed fails loudly.
- A transient provider failure comes back after a fixed delay. A terminal failure, or one past the attempt limit, marks the movie Failed and parks the message in `enrichment.dead-letter` for inspection.
- Delivery is at least once. A crash between a confirmed republish and the ack delivers a duplicate. The claim absorbs it, and exactly-once delivery is not claimed.
- **Limitation.** Crash redelivery, or competing work, inside a live claim lease is refused by the claim and acked as skipped. Recovering that movie depends on the sweeper, which is designed here but not implemented. Until it exists, such a movie stays `Pending` until something re-enqueues it.
- **Cutover.** The legacy queues `task_queue` and `task_queue_dlq` are neither migrated nor purged. This is a development-broker assumption. An environment with retained messages there needs an operational decision before deployment.
- One trace spans the publish, the queue and the processing, including across a retry. With no listener registered, the headers still carry a valid context.
- **Follow-ups outside DEV-18:**
  - the sweeper implementation;
  - the production metadata provider (DEV-303);
  - the production repository and DbContext wiring (DEV-392);
  - the shared health endpoints;
  - removing the retired projects.
- A transactional outbox, which would remove the dual write between the database and the broker, is covered by ADR-0005.
