# ADR-0003. PostgreSQL persistence with a single fresh migration

- Status: Proposed (Gate 1 closed; becomes Accepted when the DEV-19 spec PR merges)
- Date: 2026-09-30
- Ticket: DEV-19

## Context

Persistence today is the legacy `LamuFlix.Data` project. It holds `LamuFlixContext` on MySQL through
Pomelo, anemic models (`Player` plus the explicit join entities `MovieActor`, `MovieDirector` and
`MovieGenre`), MySQL-specific migrations, and a hard-coded development connection string. The legacy
`LamuFlix.Web` and `LamuFlix.Worker` hosts consume it.

The product blueprint targets .NET 10 with `LamuFlix.Infrastructure` as the adapter project
(`specs/PRODUCT.md:9`), and the constitution names PostgreSQL as the database. DEV-19 asks for:

- Npgsql in place of Pomelo;
- per-entity configurations under `src/LamuFlix.Infrastructure/Persistence/Configurations/`;
- the removal of `Player` and the explicit join entities in favour of skip navigations;
- one fresh `Initial` migration;
- no data migration from MySQL.

## Decision

- PostgreSQL 16+ via `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3 on EF Core 10.0.12. All
  Microsoft EF packages are aligned at 10.0.12, and the local `dotnet-ef` tool is at 10.0.12.
  Pomelo and every MySQL reference leave the solution.
- The context, design-time factory, configurations and migrations all live in
  `src/LamuFlix.Infrastructure/Persistence/`. Infrastructure is both the migration target and the
  startup project. The design-time connection comes only from the environment variable
  `LAMUFLIX_DESIGN_TIME_CONNECTION_STRING`; there is no literal fallback.
- There is exactly one migration lineage: a tool-generated `Initial` migration, with no hand edits,
  no seed data and no raw SQL. Any change before merge regenerates the full set.
- **No data migration from MySQL.** The PostgreSQL baseline starts empty and does not inherit any
  existing MySQL data. That data is abandoned, not converted.

## Related decisions

These are recorded in `specs/DEV-19/CONCLUSIONS.md` and are not restated or re-ruled here:

- Q1: EF maps Infrastructure persistence records, not the Core `Movie` aggregate. A future
  repository maps between them. This follows `CONTEXT.md:38-40`, which separates the Movie
  Aggregate from the EF entity. The wording in constitution IV that calls the aggregate EF-tracked
  is reconciled in Q1 by that CONTEXT decision. This ADR cross-references that reconciliation; it
  does not amend the constitution.
- Q2: explicit lowercase snake_case table, column and join-table names.
- Q4: enrichment status stored as its constitution-fixed integer value; failure category stored as
  its string code; value-object reads go through validating domain factories.
- Q7 (**proposed, pending the owner's checkbox**): retire `LamuFlix.Data` and remove the legacy Web,
  Worker and `LamuFlix.Test` projects from the solution build until DEV-388 and DEV-314/315/316
  replace them.

## Consequences

- Development and test environments need a PostgreSQL 16+ server. Integration tests use
  Testcontainers `postgres:16.4`.
- Existing MySQL data is not carried forward. The library is rebuilt by rescanning.
- Moving to EF Core 10 ties the provider and tooling to the .NET 10 LTS line. The next major EF
  upgrade will add a migration on top of `Initial`, not replace it.
- If the owner approves Q7, the legacy Web UI and legacy enrichment worker stop working from this
  merge until their replacements land. If the owner declines, DEV-19 is sequenced behind those
  replacements instead.
- Runtime database wiring for Api and Worker, and the repository and catalog adapters, are
  separate tickets (DEV-301, DEV-302, DEV-307, DEV-308).
