# Keep local player execution behind a proven local HTTP boundary

DEV-458 requires file-existence checks, an unmapped-player 422, enabled-LocalPlay startup refusal on non-loopback binds, and verification that shipped proxies cannot expose launch remotely. With `Features:LocalPlay=true`, every effective API listener must be proven loopback before any request is served, and `POST /api/movies/{id}/play` additionally requires a loopback raw peer and no forwarding-provenance headers. IPv4-mapped IPv6 peers/listeners are normalized before loopback checks; unknown peers/listeners fail closed. LocalPlay disabled imposes no new listener restriction.

A loopback proxy stripping provenance cannot be distinguished from a local client. Shipped nginx denies the play route with proxy 403; the Aspire web endpoint proxy remains disabled and no endpoint proxy may forward play. Direct API access is governed by the request guard and startup invariant. The shipped LocalPlay-disabled default is retained but does not substitute for these pinned exclusions. Actual runtime smoke must prove the shipped paths cannot elicit a launch; a separate named LocalPlay-enabled loopback host using the same build/player/file fixtures supplies the positive control (CONCLUSIONS Q8). Such a stripping proxy exposing play with LocalPlay enabled is unsupported. We reject an absolute arbitrary-proxy claim and avoid introducing a token, mTLS or another execution channel beyond this ticket's existing HTTP design.

Within the existing Infrastructure launcher, reuse IFileSystem to check the selected file before player resolution and process start: missing file throws the existing parameterless NotFoundException and returns fixed 404 title Not Found with no detail, unmapped format existing 422 with safe format-level detail, and neither starts a process or appends playback history. Peer/header refusals preserve fixed 403 title Forbidden with no detail. Existing mappings omit exception messages; tests pin absent detail and no message/type/path/peer/header leakage. No handler/Core exception edit or custom 403/404 detail is required or approved (CONCLUSIONS Q9). Preserve DEV-438 selection, existing process-start semantics and one file argument. The check/start race remains a generic start failure (500, no retry/history), rather than pretending the filesystem and external process are atomic.

The cost is deliberate refusal of proxied launching and ambiguous bindings. Following the hosting decision in `specs/DEV-458/CONCLUSIONS.md` Q7, use a dedicated API `IHostedService.StartAsync`, registered in `Api/Program.cs`, with synchronous validation before server startup; ServiceDefaults is unchanged. Reconcile framework configuration and the server-address feature using documented precedence, using the existing named framework surfaces and the owner-approved Constitution VII exception for this validator to read IConfiguration Kestrel / Endpoints / Url outside options binding (CONCLUSIONS Q10). This exception covers section presence/absence and endpoint Url values only; no new options record or broad raw-key access is approved. No code-defined Kestrel endpoints may be introduced: review and a source-search receipt enforce that invariant because no documented public pre-start enumeration surface was found. Actual-startup tests must prove precedence, registration/concurrency ordering and pre-bind refusal; shipped Aspire injection and nginx/Aspire launch protection still require runtime evidence. The supplied .NET 10 accessor recon found no permitted pre-bind reader of Kestrel-section Url values or section absence. Patron identified no compliant alternative. The owner selected Option A on spec PR #336, approving that bounded VII departure (CONCLUSIONS Q10); this is an explicit exception rather than a claim of VII conformance. Q2 is not rescoped. New options records, reflection, code endpoints and fail-all LocalPlay implementations remain unapproved. Runtime proof obligations remain unchanged. No new dependency, port, project, layer, database schema or secret is introduced.

Basis: ticket scope and cited section 2.3 rulings recorded in `specs/DEV-458/CONCLUSIONS.md` Q1-Q10; `specs/PRODUCT.md` sections 3/5; constitution Principles I/VII and API/contract rules. Hosting rationale uses the supplied .NET 10 [hosted-services startup ordering](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0#ihostedservice-interface), [application startup sequence](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/startup?view=aspnetcore-10.0), and [Kestrel endpoint configuration](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0) sources retained in CONCLUSIONS Q7. These sources motivate the design; required runtime evidence remains separate. Implementation footprint, review loop terms and mandatory nginx/Aspire verification are defined in `specs/DEV-458/brief.md`.
