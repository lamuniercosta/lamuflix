# ADR-0008. Polling for enrichment status in P1; SignalR deferred

- Status: Accepted
- Date: 2026-10-10
- Ticket: DEV-319 (parent DEV-285)

## Context

DEV-319 delivers telemetry instrumentation and this ADR. Enrichment runs asynchronously: the import path persists a movie and enqueues an enrichment request, and a RabbitMQ consumer later resolves the lookup, retries within bounds, and settles terminal failures to a dead letter. Clients need to learn when enrichment for a movie has resolved.

The decisions are recorded in [brief.md](../../specs/DEV-319/brief.md) P6 and [CONCLUSIONS.md](../../specs/DEV-319/CONCLUSIONS.md) P6. The constitution already settles the position: enrichment status is delivered by polling in P1 and SignalR is a stretch item (constitution.md:473, :500), so this ADR records rather than departs.

No polling delivery path and no SignalR hub exist anywhere in the tree: a case-insensitive search for SignalR returns zero lines, and every polling mention sits under `specs/` (recon-DEV-319:136-138). The ticket delivers the ADR only.

## Decision

Enrichment status is delivered by client polling in P1. Push over SignalR is deferred and is not designed, referenced, or depended upon here: no hub, no package, no endpoint, and no polling implementation is added by this ticket. Any polling endpoint or SignalR hub/package would add to what the ticket delivers and is therefore out of scope.

Polling fits the existing architecture: enrichment already exposes durable, per-movie terminal state (enriched, not-found, failed) through persistence and dead-letter settlement, so a client can re-read status until it resolves. Push would add a connection and broadcast lifecycle the P1 scope does not need, with no P1 consumer waiting on it.

This ADR invents no polling interval, endpoint, response shape, or future implementation commitment. Those remain later decisions when a polling surface is specified.

## Consequences

- Readers can rely on polling as the Accepted P1 answer for enrichment status; SignalR stays a deferred stretch item.
- The ticket's acceptance is the existence and Accepted status of this document; no code, test, or package change proves it.
- A future polling endpoint or SignalR introduction requires its own specified, reviewed change; this ADR constrains neither its design beyond the P1 polling position recorded here.
