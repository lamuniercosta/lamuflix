# 0028. Confirmed enrichment outbox relay

- Status: Draft
- Date: 2026-10-25
- Ticket: DEV-420

## Context

[ADR-0027](0027-transactional-outbox-enrichment.md) accepts the transactional enrichment outbox and assigns staging to DEV-329 and relay delivery to DEV-420. DEV-329 stages an enrichment request before the shared movie save; its approved design still directly enqueues after that save. DEV-420 completes the two-handler cutover so a durable request can succeed while RabbitMQ is unavailable and be published later by the relay. The sweeper remains a safety net.

The prerequisite contract is the unchanged four-column `outbox_messages` table (`id`, `payload`, `created_at`, `processed_at`) and partial pending index `(created_at,id) WHERE processed_at IS NULL`. `IEnrichmentOutbox.Stage(EnrichmentRequested)` tracks a row in the movie repository's scoped DbContext without saving or publishing. Payload is immutable UTF-8 Web JSON for the existing `EnrichmentRequested(MovieId, Attempt)` type. The movie write and outbox insert commit together.

Basis: task note `DEV-420:27-30`; `recon-DEV-420:44-196`; [brief.md](../../specs/DEV-420/brief.md), Q2-Q12 and post-grill C1; the cited Patron rulings in [CONCLUSIONS.md](../../specs/DEV-420/CONCLUSIONS.md); [plan.md](../../specs/DEV-420/plan.md); ADR-0027. This draft records those settled decisions only. It does not establish ADR acceptance, plan freeze, Gate 1, or implementation clearance.

## Decision

Use one non-overlapping Infrastructure `OutboxRelayHostedService`, composed by `AddLamuFlixOutboxRelay` in the Api host. Each pass uses a fresh DI scope/DbContext to materialize at most `BatchSize` durable unprocessed rows ordered by `(CreatedAt,Id)`. Deserialize the stored Web JSON into the existing request type, preserving MovieId and Attempt, and publish sequentially through the existing confirmed mandatory `IEnrichmentQueue` path. Do not hold a database transaction or connection across broker waits. Only after confirmation settles, assign `ProcessedAt` using injected `TimeProvider` and commit that individual marker before advancing. No batch-wide marking, publisher rewrite, new Core relay port, generic persistence layer, schema change, or new dependency is introduced (Q2-Q3).

Abort a pass at its first payload, database, publish/confirm, or marker-save failure; dispose its scope and preserve committed markers. Unconfirmed work remains unprocessed. Resolve an uncertain marker commit by a later fresh database read rather than assuming rollback. Retry fresh ordered reads with capped exponential backoff. Nack, mandatory return, timeout, and connection failure never justify marking a row. An invalid oldest payload blocks progress; do not skip, delete, quarantine, or add retry metadata. Host shutdown exits cleanly without a synthetic failure or retry delay (Q4).

Bind startup-validated `OutboxRelayOptions` under `OutboxRelay` using the exact defaults and bounds in the brief's Options and scheduling section. Poll immediately; after every successful pass, including full and empty batches, delay `PollInterval`. Consecutive failures use `FailureBackoffMin * 2^(failures - 1)`, saturating safely at `FailureBackoffMax`; a successful pass resets the sequence. Use injected `TimeProvider` for timestamps, delays, and timeouts, without jitter or an enable/disable flag. Link each publish timeout to host cancellation; save its marker under the host token rather than an expired publish token (Q5).

Run independently scheduled cleanup within the same worker, first due at startup and then each `CleanupInterval`, including after a failed publish pass. In a separate fresh scope, select at most `CleanupBatchSize` rows ordered by `(ProcessedAt,Id)` and delete only rows with non-null `ProcessedAt` strictly older than `now - ProcessedRetention`, rechecking that predicate during deletion. Retain cutoff-equal and unprocessed rows regardless of CreatedAt. Cleanup failures are separately observable, leave committed publication progress intact, and retry at the next cleanup interval (Q6).

Expose the cached, thread-safe worker state through `outbox-relay` with the existing Ready tag, readiness endpoint, and HTTP mapping. After a successful publication pass, sample backlog in a fresh scope; sample failure fails the pass. Health is Unhealthy before the first successful sample, after a failed pass/sample, or on unexpected worker stop; otherwise Degraded for oldest pending age at least `BacklogAgeWarning` or the latest cleanup failure; otherwise Healthy. A later successful pass or cleanup clears its respective fault. Health and metric callbacks perform no database I/O. Withhold invalid/failed backlog samples rather than emitting stale values or false zeros; a successful empty sample yields zero count and age (Q7, Q12).

Keep instruments in Infrastructure `OutboxRelayMetrics`, consuming six centralized `const` names in existing `src/LamuFlix.Core/Pipeline/TelemetryConstants.cs`: `lamuflix.outbox.pending`, `lamuflix.outbox.oldest_pending_age`, `lamuflix.outbox.published`, `lamuflix.outbox.failures`, `lamuflix.outbox.retention.deleted`, and `lamuflix.outbox.retention.failures`. Published counts only confirmed-and-durably-marked rows; failure counters count failed passes or cleanup runs respectively. Keep labels low-cardinality, without MovieId, payload, or exception-message labels. Structured relay/cleanup failure logs allow only outbox row id (when row-scoped), exception type name, and a stable internal error category. Never pass an exception object to the logger or emit raw Message, ToString(), stack trace, inner-exception text, payload-derived values, or sensitive connection/configuration details (Q7; post-grill C1; Patron plan-challenge logging ruling in [CONCLUSIONS.md](../../specs/DEV-420/CONCLUSIONS.md), lines 233-236).

Remove only the queue dependency and direct enqueue from `ImportMovieFolderCommandHandler` and `RequestEnrichmentCommandHandler`. Preserve Stage before the shared save, both-or-neither atomicity, and propagation of staging/serialization/save errors and cancellation. Successful durable save succeeds independently of broker availability. Do not add handler retries or replay failed scopes. Other enqueue callers and the sweeper remain unchanged (Q2).

## Assumptions

- One Api instance owns the relay operationally; concurrent relays across Api instances are outside ticket scope. There is no ownership/claim protocol for multiple relays.
- The approved DEV-329 packet is a design prerequisite, not proof of landed implementation. Phase B must verify landed DEV-329 schema/Stage/payload/save contracts and DEV-419 against current main and resolve pickup drift before code; missing prerequisites are never replaced locally.
- The exact Q9 delivery boundary is 24 production/test files after Patron's post-grill C1 ruling, including only the six metric-name constants in `TelemetryConstants.cs`. This ADR is a separate Phase A document. Additional delivery files require a cited ruling.
- No public API/OpenAPI/frontend, package, project, architectural layer, database schema, LocalPlay, secrets, or harness-threshold change is part of this design. Root vocabulary and constitution history remain unchanged; ADR-0027's constitution follow-up remains separate.

## Consequences

Delivery is deliberately at least once: a confirmed publish followed by a failed or uncertain marker commit can be published again. Existing enrichment claims absorb duplicate work. A durable processed marker prevents normal republishing on later passes or restart. Ordering applies to each pending batch query; it is not a global FIFO or exactly-once guarantee. Vocabulary remains precise: staged means tracked before save, durable means committed with the movie, unprocessed means null ProcessedAt, confirmed means settled broker acceptance, processed means a durably committed post-confirm marker, and expired processed means ProcessedAt strictly before the retention cutoff (Q3-Q4, Q12).

Per-row marker saves and a delay after every successful batch bound throughput. Poison rows can cause head-of-line blocking and unhealthy readiness. Bounded scheduled cleanup means retention is an eligibility threshold rather than a maximum storage age; eligible rows may wait for later runs. Cached backlog telemetry exposes valid samples without doing database work in callbacks. These costs preserve durable work and make failed progress visible (Q3-Q7).

Phase B proof uses real PostgreSQL and RabbitMQ Testcontainers for both handlers committing during broker outage, recovery delivery, payload parity, post-confirm marking, restart behavior, batch order/limits, mandatory returns, and retention boundaries. Controlled publisher faults against real PostgreSQL cover pre-confirm, mid-batch, and post-confirm marker failures and fresh-scope recovery. Deterministic TimeProvider tests cover scheduling, shutdown, backoff, poison rows, cleanup isolation, options, and health/metric transitions. Composition tests retain the sweeper and exercise the actual worker for relay delivery proof. Reuse existing packages and test conventions; never mock driver behavior for query translation or serialization (Q8-Q10).

This draft elaborates ADR-0027's relay follow-up while preserving its accepted guarantees and history. Plan challenge, freeze, owner Gate 1, implementation, gates, review, and merge remain separate later steps.
