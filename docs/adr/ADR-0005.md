# ADR-0005. Dual-write mitigation for enrichment: sweeper now, transactional outbox as a stretch

- Status: Accepted
- Date: 2026-09-30
- Ticket: DEV-18 (parent DEV-283)

## Context

Enrichment state is written in two places that share no transaction: the movie row in the database and the enrichment message in RabbitMQ (ADR-0004). The Core handlers that start enrichment persist the movie as `Pending` and then call `IEnrichmentQueue.EnqueueAsync`. The consumer does the reverse for a terminal failure: it marks the movie Failed, saves, and then republishes to `enrichment.dead-letter`.

This is a classic dual write. Whatever order the two writes take, one can succeed while the other fails:

- **Database committed, publish failed.** A broker outage, a nack or a returned message leaves a `Pending` movie with no message anywhere. Nothing will ever process it.
- **Publish succeeded, database not committed.** The message refers to state that was never saved. The claim (`TryClaimForEnrichmentAsync`) refuses a movie that is not `Pending`, so the message is acked as skipped and does no harm.
- **Crash inside a claim lease.** The redelivered message is refused by the live claim and acked, and the movie stays `Pending` (the ADR-0004 limitation).

Only the first and third cases lose work. In both, the movie is left `Pending` with no message, or with a message that has already been consumed.

## Decision

1. **Publish failures are loud.** DEV-18 publishes with confirms and mandatory routing (ADR-0004). `EnqueueAsync` throws unless the broker stored and routed the message, so the caller knows the second write failed. It never silently reports success.
2. **Stranded work is recovered by a sweeper, not by distributed transactions.** The recovery design is the `StrandedMovieSweeper` described in ADR-0004. It periodically finds `Pending` movies whose last attempt is older than the claim lease, or that never had a queued message, and re-enqueues them through `RequeueStrandedMoviesCommandHandler`. It needs only the existing `Status`, `LastAttemptAt` and `EnrichmentAttempts` columns. Duplicates it creates are absorbed by the claim, which fits the at-least-once model.
3. **DEV-18 records the sweeper design and does not implement it.** Implementation is a follow-up ticket. Until it lands, stranded movies are recovered by invoking `RequeueStrandedMoviesCommandHandler` or requesting enrichment again. How the sweeper hands a claim off remains an open owner decision (DEV-299 Q1, DEV-316).
4. **A transactional outbox is the stretch goal and is not part of DEV-18.** An outbox writes the message to an outbox table in the same database transaction as the movie change, and a relay publishes and marks it sent. That removes the "database committed, publish failed" window entirely. It needs a new table (a schema change) and a relay hosted service, both outside DEV-18's scope. It is worth doing if the sweeper's recovery latency (up to one claim lease plus one sweep interval) proves unacceptable, or if more message types need the same guarantee.

## Consequences

- No enrichment work is lost permanently once the sweeper exists. Until then, stranded `Pending` movies need a manual re-enqueue, and this is a known gap.
- Recovery is eventual, not immediate. A stranded movie waits up to one claim lease plus one sweep interval.
- Consumers must stay idempotent, which the claim already provides. The sweeper and an outbox relay would both produce duplicates.
- The outbox, if adopted later, would need its own ADR, a schema change and a relay. It would supersede point 2 for the publish side, and the sweeper would remain the safety net for in-lease crashes.
