# Separate feature generation from metadata enrichment

DEV-414 requires asynchronous plot embedding, MovieId upsert, retry/dead-letter handling, and recovery of movies without stored features. Keep feature generation as a separate post-enrichment lifecycle using the existing embedding generator, movie-features repository, RabbitMQ publisher, and features topology, leaving metadata `EnrichmentStatus` and `EnrichmentAttempts` untouched. Recover missing features through an independently guarded sweeper pass that starts a fresh transport chain at Attempt 1, accepting repeated inference and later recovery after dead-lettering without adding persistent feature status or lifetime retry suppression.

This records the frozen Patron decisions in [brief.md](../../specs/DEV-414/brief.md), Q2-Q9 including the Q4 continuation, with their cited bases and full exchanges in [CONCLUSIONS.md](../../specs/DEV-414/CONCLUSIONS.md). The corresponding requirements and approach are in [spec.md](../../specs/DEV-414/spec.md) and [plan.md](../../specs/DEV-414/plan.md); terminology follows [CONTEXT.md](../../CONTEXT.md).

## Consequences

- The handler loads the current plot through `IMovieRepository`. Missing movies and null/whitespace plots are successful acknowledged no-ops. A nonblank plot generates one vector through `IEmbeddingGenerator<string, Embedding<float>>`, applies existing snapshot/repository validation, and upserts through `IMovieFeaturesRepository`, using injected `TimeProvider` for `ComputedAt`. Existing rows do not skip generation: duplicate and concurrent deliveries retain one MovieId row with last-write-wins vector/timestamp updates, at the cost of repeated inference. No plot hash, model/version persistence, or schema change is introduced (Q2-Q3).
- `EnrichmentOptions.MaxAttempts` bounds each feature transport chain. Retryable failures below that limit publish Attempt+1 to `features.retry`; permanent or exhausted failures go to `features.dead-letter`. Typed embedding failure categories take precedence over the existing classifier; feature failure headers allow only sanitized `provider_unavailable`, `rate_limited`, `invalid_response`, and `unknown` categories. Invalid payloads, Attempt below 1, and invalid vectors are permanent `invalid_response`; requested shutdown requeues the original unchanged (Q4 and continuation).
- Reuse the existing publisher with persistence, confirmations/tracking, mandatory publication, and awaited publication. Acknowledge only after successful upsert/no-op or completed retry/DLQ publication; thrown or cancelled publication never permits acknowledgement and preserves/requeues the original. Configured options do not establish broker-ack/nack/return await guarantees or exactly-once durability. Live RabbitMQ tests must prove retry/DLQ publication, failed publication without acknowledgement, and the existing unroutable expectation; failure blocks delivery (Q4 continuation, Q8).
- On each existing `SweepInterval`, a database-side anti-join selects nonblank-plot movies with no `movie_features` row, without an enrichment-status predicate or N+1 lookups. Recovery enqueues `FeaturesRequested(MovieId, 1)` without embedding, claiming, or mutating metadata. Enrichment recovery retains its Pending-plus-lease semantics; neither guarded pass suppresses the other except during shutdown. Prior DLQ entries remain, and persistently failing movies remain eligible indefinitely; in-flight duplicates and fresh chains after terminal failure are accepted costs (Q5-Q6).
- Extend existing ports and composition with explicit feature handlers and consumer/routing types, without a generic transport framework or second publisher. Feature activation requires both movie repositories, the embedding generator, and the RabbitMQ publisher, independently of `IMetadataProvider`; incomplete hosts log inactivity without resolving missing prerequisites. Separate feature liveness and `features-consumer` readiness use the existing readiness endpoint, with producer-to-consumer-to-embedding/upsert tracing. Real PostgreSQL/RabbitMQ integration tests and the existing fake generator provide the approved proof; no new dependency, layer, or public HTTP contract is added (Q6-Q9).
