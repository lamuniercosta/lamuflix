# ADR-0006. Failure categories separated from exception types; raw errors never leave logs

- Status: Accepted
- Date: 2026-09-27
- Ticket: DEV-295 (parent DEV-282)

## Context

Metadata enrichment failures currently expose raw exception details. That can leak internal URLs, stack traces, and system details to callers. Callers need a stable category for retry decisions and safe messaging, while diagnostics keep the raw exception.

## Decision

Classify exceptions into `EnrichmentFailureCategory` values. Callers see only the category `Code`, `IsRetryable`, and `SafeDescription`. Raw exception text, stack traces, and URLs stay in logs and OpenTelemetry spans. They do not go into database columns or API responses.

`EnrichmentFailureClassifier.Classify` is a pure static function. It does not log and it does not emit telemetry. Pipeline retry wiring and span emission are downstream.

## Consequences

- Callers get a closed set of safe messages.
- Retry policy can follow `IsRetryable` (for example `RateLimited` waits and retries).
- Raw error context remains available for diagnostics in logs and traces.
- **Limitation (follow-up 1):** A linked cancellation source created with `CancelAfter` is not distinguished here. The caller checks `CancellationToken.IsCancellationRequested` before `Classify` when that distinction matters.
- **Follow-up 2:** Pipeline retry wiring is downstream.
- **Follow-up 3:** OpenTelemetry emission is downstream.
