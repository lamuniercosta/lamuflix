# Explicit movie reviews and separate recommendation preferences

Status: proposed for DEV-461 specification approval. Patron approved the design during grill questions Q1-Q8; this ADR does not grant Gate 1 or implementation clearance.

DEV-461 replaces the card Not interested action with mutually exclusive thumbs reviews and requires positive and negative reviews to change both For You and Related recommendations through plot embeddings and metadata. A movie has one canonical Review (`None`, `Liked`, `Disliked`), independent of Watched and Watchlist. Persist it on the existing Movie aggregate and record, migrate existing `IsNotInterested` marks to `Disliked` (otherwise `None`), and retain legacy not-interested endpoints and flags as compatibility projections rather than a second source of truth. An idempotent `PUT /api/movies/{id}/review` sets the canonical state.

Keep the existing recency-weighted viewing-history profile, excluding Disliked movies from its positive inputs. Extend Taste Profile with separate liked and disliked aggregates for plot, genres, cast, and director, including reviewed movies with no playback history. Each movie contributes one equally weighted review signal. Combine bounded, nonnegative channel affinities as `baselineSimilarity + LikedReviewWeight * likedAffinity - DislikedReviewWeight * dislikedAffinity` inside the existing profile blend coefficient. Do not clamp this signed result back to a nonnegative range. Review coefficients and channel weights remain configurable and validated.

Separate review aggregates preserve nonnegative weighted-Jaccard metadata preferences and avoid cancelling liked and disliked vectors inside a single signed centroid. A second persisted negative flag would permit contradictory review state; storing reviews without changing scoring would fail the ticket. The cost is a data migration, compatibility adapters, profile evidence for truthful reasons, and tests across ranking, persistence, caches, and generated API contracts. Successful canonical and legacy review updates invalidate the existing Taste Profile cache so subsequent recommendation requests use the new state.

The Phase 2 step 6 ruling specifies Review as the approved SmartEnum with literal lowercase Names `none`, `liked`, `disliked`, persisted by Value through an EF converter. Raw-string request binding permits semantic validation through the existing Infrastructure validation decorator without changing the approved 400/422 boundary. Responses expose Name strings. No new package or port is introduced.

The same migration backfills Review and drops the legacy `IsNotInterested` mapping/column. Down reconstructs the boolean as true only for Disliked, false for None or Liked; downgrading therefore loses the positive-review distinction. Public compatibility routes and fields remain projections.

Preserve repository-driven post-commit invalidation: increment the process-local generation, then remove the cache tag. A post-commit invalidation failure propagates 500 while keeping the committed database write, matching incumbent behavior; 204 requires completed invalidation. Database atomicity does not extend to the cache. The UI rollback is provisional and reconciled through authoritative refresh and idempotent review retry. Retain generation checks for in-flight fills and add failed-tag-removal-then-read coverage. No retry queue, new invalidation port, or distributed freshness guarantee is added. Freshness/ranking tests use controlled candidate pools.

This ADR remains Proposed until Gate 1 acceptance, when its owner records Accepted. This status does not grant implementation or merge clearance.
