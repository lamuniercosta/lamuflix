## Q3 - Fallback, exhaustion, and pass-through

Keel: What result should exhaustion return when eligible failures and misses are mixed? Ticket item 2 fixes advancement on NotFound/RateLimited/ProviderUnavailable and stopping on InvalidResponse/Unknown. I recommend first Found wins, any other Failed category stops immediately (including defensive DuplicateImdbId), and if every provider is exhausted return the first eligible Failed in provider order if one occurred, otherwise NotFound. Thus OMDb unavailable then TMDb miss remains retryable rather than permanently marking the movie NotFound (recon original section 7). Both eligible failures return the OMDb category, preserving deterministic ordering; a later stop failure wins immediately. Forward the same lookup and token unchanged, including ManualImdbId; propagate caller cancellation and unexpected exceptions, with no fallback on exceptions. No catches or extra retry loop in the chain. Cost: outage-plus-miss retries even if the surviving vendor has no match. Approve this complete result algorithm as the documented fallback rule, or rule its correction with cited basis.

Patron:
[from Patron] Verdict: Approved — adopt the exact fallback and exhaustion algorithm: first `Found` wins; advance only on `NotFound`, `Failed(RateLimited)`, or `Failed(ProviderUnavailable)`; stop immediately and return the failure on any other `Failed` category (`InvalidResponse`, `Unknown`, or defensive `DuplicateImdbId`); upon exhausting all configured providers, return the first recorded eligible `Failed` result in provider order if any occurred, otherwise `NotFound`.
- Fallback advancement and immediate stop (`recon-DEV-423-2` §B items 1–2, AC 1–2; `recon-DEV-423` §6.1 line 60): ticket item 2 mandates advancing on `NotFound`, `RateLimited`, or `ProviderUnavailable` and stopping on `InvalidResponse` or `Unknown` ("so bad data is not hidden by a second provider"); stopping on any non-eligible `Failed` (including `DuplicateImdbId`) makes the branch exhaustive without a second retry loop or field merging.
- Exhaustion precedence preserves retryability (`recon-DEV-423` §7 lines 105–106): `ProcessEnrichmentCommandHandler` treats `NotFound` as terminal (`movie.MarkNotFound(now)`, never retried) while `RateLimited` and `ProviderUnavailable` route through `EnrichmentRetryPolicy.Decide` for retry; returning the first eligible `Failed` in provider order when mixed with `NotFound` prevents a transient primary outage plus secondary miss from permanently stranding a movie as `NotFound`, and deterministically preserves primary failure semantics (such as `RateLimited` delayed retry) when both providers fail eligibly.
- Pure pass-through of `MetadataLookup`, cancellation, and exceptions (`recon-DEV-423` §6.2 line 68, §7 line 108; `recon-DEV-423-2` §D line 81): `ChainedMetadataProvider` forwards `lookup` (including `ManualImdbId`) and `ct` unchanged to each provider and performs no `try`/`catch` or internal retry — adapters already map transport/timeout/circuit faults into `Failed(ProviderUnavailable)`, while caller `OperationCanceledException` and unexpected exceptions propagate directly to the handler.
