No audio or other codec IDs keep existing raw behavior, including named supported codecs. Distinguish a failed probe from a successful probe with no audio and use existing API error handling for the former, with cancellation propagated. Keep the prerequisite proof responsible for verifying the probe executable and machine-readable metadata on cluster and Compose; if unavailable, return for a ruling on provisioning rather than assuming it is installed. This makes dispatch deterministic and prevents filename heuristics, with a probe cost that AC2 requires us to avoid or measure on the raw path. Basis: recon lines 13, 16–17, 32–39; Q1–Q2. Please rule on the policy, including the existing-versus-new dependency boundary for the probe.

[from Patron] DEV-572 Q3 ruling: ACCEPT with two amendments. Accepted: probe the real media metadata with ffprobe JSON output through the existing SystemProcessRunner (recon 17). Pick the first audio stream flagged default, otherwise the first audio stream in input order (answers the ticket Open question on tracks), and map that same stream explicitly. Convert only when its codec is AC3, E-AC3 or DTS (AC1). No audio, AAC/MP3/Opus/Vorbis, or any other codec stays raw (AC2). No filename heuristics: FolderNameCleaner (recon 16) is not a signal. Cancellation propagates. Amendment 1, probe timing: probe at play time and cache the result in memory per file (path plus size plus last-write time) so the many range requests of one playback, and later plays, do not re-probe. Amendment 2, failed probe: log a warning and serve the current raw stream, not an API error, so a probe fault cannot break playback that works today (AC2). Cancellation still propagates and is not treated as a failure. Dependency boundary (§5 item 1): no new NuGet or npm package and no ffmpeg wrapper library. ffprobe is the binary from the ffmpeg install the API image already has (Dockerfile.api line 18, recon 38). If it is missing, return for a provisioning ruling rather than assuming it.

## Q4 — Conversion ownership, retention, and cleanup

[from Keel] DEV-572 Q4 — What lifetime and ownership should temporary conversion artifacts have across HTTP requests? I recommend one in-flight conversion per source version per API instance, shared by concurrent authorized requests. Cancel the child and delete all partial output when the last waiting request disconnects or the conversion fails. Publish only completed output, keep it in a bounded API-owned scratch area across normal Range responses, and allow active readers to finish before deletion. On converted response abort, mark the asset for deletion once idle unless another request is already using it, and prove real Chromium seeks still work when it aborts an old request while issuing the new one. Apply configurable size/concurrency limits and idle expiry, isolate the scratch area from the library, and clean owned orphan files on startup. For a known conversion failure I recommend existing API error handling without redirect or silent raw fallback. This protects AC6 while preserving AC4, and requires testing the abort/seek race and bounded cleanup. Basis: AC1, AC4 and AC6 (recon 32, 35, 37), Q1–Q3. Please settle the cleanup semantics for normal Range completion versus browser or client disconnect.

[from Patron] DEV-572 Q4 ruling: ACCEPT with one correction on abort semantics. Accepted: one in-flight conversion per source version (path plus size plus last-write time, as in Q3) per API instance, shared by concurrent authorized requests. When the conversion fails, or the last waiting request disconnects before it finishes, kill the ffmpeg child and delete all partial output (AC6, recon 37). Publish only completed output, by atomic rename into an API-owned scratch area isolated from the library (ticket intent: library read-only, recon 30). Clean owned orphan files on startup. Size, concurrency and idle-expiry limits are configurable. Defaults are taste-level for the plan to propose, logged [assumed], and answer the ticket Open question on concurrency. Correction: a completed asset is NOT marked for deletion when a converted response aborts. Chromium aborts range requests routinely while seeking (AC4, recon 35), so deleting on abort would force re-conversion mid-session. Once complete, the asset is governed only by idle expiry, size-bound eviction (least recently used first, never while a reader holds it), source-version change, and startup cleanup. Basis: AC6 targets leftovers from failed transcodes or disconnects, meaning processes and partial files; a published, bounded, expiring asset is neither. The proof still exercises the Chromium abort-plus-new-range race. Known conversion failure: accept existing API error handling, with no redirect and no silent raw fallback (a silent movie would violate AC1, recon 32). Unlike Q3 probe failure, a conversion failure means we already know the audio is unplayable. Do not add or advertise a new status code on the route (Q1).
