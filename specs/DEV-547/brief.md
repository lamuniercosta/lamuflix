## Grill questions and rulings

1. **Which API surface?** Patron approved dedicated `GET /api/version` under the existing `/api` group, returning HTTP `200 OK` with `{ release, commit }`. `release` is a nullable string and `commit` is a string. Generate OpenAPI and TypeScript from the C# DTO. This keeps the API independent of DEV-560. Basis: Wanted 5, Done when 2, `recon-DEV-547:12–16,29,33,58,63`.
2. **How should build and release metadata flow?** Patron approved `LAMUFLIX_COMMIT` and `LAMUFLIX_RELEASE`. Both CI Docker jobs pass the exact full source SHA as a build arg to both Dockerfiles, which persist it in the final images. Home promotion injects the release into both pods from the `RELEASE_TAG` used in `RELEASE.json`, with an empty value for manual promotion. Compose supplies a configurable commit through build args and an empty release. Preserve the baked commit when no runtime override is supplied. The API reports the full commit, uses `unknown` for unset, empty, or whitespace local commit metadata, and serializes unset, empty, or whitespace release metadata as explicit JSON `null`. Basis: Wanted 3–5 and Done when 2–3, `recon-DEV-547:20–24,56–58,63–64`.
3. **Where and how should the app show the version?** Patron approved consuming the generated `GET /api/version` type in the DEV-560 status page if it has landed by Phase B pickup, or in one `App.tsx` footer otherwise. Display `<release|dev> (<first 8 SHA characters|unknown>)`, for example `v0.1.0 (8a2deb9b)` or `dev (8a2deb9b)`. Omit the line while loading or on failure. Basis: Wanted 5 and Done when 7, `recon-DEV-547:15–16,29,58,68`.
4. **When can the tag be pushed and what closes the ticket?** Patron approved parallel changelog/README and implementation work, with DEV-546 required first. Build and delivery verification precede the user merge. The authorized release operator pushes `v0.1.0` only after both tickets are on `main` and the nightly gate passes on that exact target commit. The tag run, GitHub Release, release manifest, and port 3100 must agree with that target. Rigger posts the tag-run link and version-line screenshot to the ticket before closure. Basis: Wanted 2 and 6, Done when 1 and 4–8, `recon-DEV-547:22–28,55,59,62,65–76`.
5. **What must pass before merge?** Patron approved the API integration and normalization cases, contract generation and drift check, web state tests, checks of CI build inputs and tagged/manual promotion rendering, offline deployment parity, and configured C# and web gates listed below. Live release verification follows Q4. Basis: Wanted 3–5 and Done when 2–3, `recon-DEV-547:14,16,20–24,56–58,63–64` and repo gate policy.
6. **What closes review and the grill?** Patron approved the two-round cap, full Size M review, the frozen scope above, and the closing bar below. Patron confirmed the grill could close. Basis: `task-pipeline` Size M path, charter §2.3, `recon-DEV-547:28,54–76`.
