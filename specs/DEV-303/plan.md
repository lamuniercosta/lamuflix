## Summary

Fill the Core `IMetadataProvider` port with a sealed `OmdbMetadataProvider` in `Infrastructure/Adapters/`: a typed `HttpClient` behind the standard resilience handler, mapping OMDb responses to `MetadataLookupResult` and classifying every expected outcome as a result rather than an exception. Bind the Q4 resilience numbers to a new validated `MetadataProviderResilienceOptions` under the `Omdb:Resilience` key, add the `Metadata.Lookup` span on the existing activity source, a passive `metadata-provider` health check, Api host wiring, and a WireMock.Net test matrix covering outcomes, mapping, retry/Retry-After/timeout/breaker behaviour, cancellation, request shape, secrecy, telemetry, health and composition.

## Approach (brief §5.1, as amended by D1–D7)

- **Adapter shape**: `public sealed partial class OmdbMetadataProvider` with a primary constructor over `HttpClient`, `IOptions<OmdbOptions>`, `TimeProvider`, `ILogger<OmdbMetadataProvider>` and `MetadataProviderHealthState` (D3: the full list, with the options dependency, and `MetadataProviderHealthState` public so CS0051 is satisfied); the key is read from the injected `IOptions<OmdbOptions>`. The type is split across three files: the flow and classification in `OmdbMetadataProvider.cs`, the mapping in `OmdbMetadataProvider.Mapping.cs`, the `[LoggerMessage]` members in `OmdbMetadataProvider.Log.cs`. `FindAsync` is a thin orchestrator in this order: start the `Metadata.Lookup` activity on the provider's own `private static readonly ActivitySource Source` → build the escaped relative request URI → `GetAsync(uri, HttpCompletionOption.ResponseHeadersRead, ct)` through the pipeline → classify → deserialize on 200 → map → set the outcome on the activity and record it in the health state. Each step is a private helper so the method clears the ≤ 6 refactor gate (Q6, Q11).
- **Classification (Q6 table)**: the first matching row wins. Caller cancellation — during the send, a retry wait or the body read — is rethrown. Then 200 + `Response:"True"` + valid title → `Found`; `Response:"False"` + `"Movie not found!"` → `NotFound`; 401 → `Failed(InvalidResponse)` plus the advice warning; a final 429 → `Failed(RateLimited)`; a final 5xx/408, `TimeoutRejectedException`, `BrokenCircuitException`, `HttpRequestException`, or a total-timeout cancellation the caller did not request → `Failed(ProviderUnavailable)`; every other case (other 4xx, malformed or DTO-incompatible JSON, missing or unrecognised `Response`, `Response:"False"` with another `Error`, missing/blank/`N/A` Title) → `Failed(InvalidResponse)`. Only those exception types are caught, so programming errors propagate. The classification is split into one private helper per status class rather than one long `switch`, per §5.4.
- **Request (Q7)**: `?apikey=…&t=…&type=movie[&y=…]`, each value through `Uri.EscapeDataString`, against the configured `BaseUrl`.
- **Mapping (Q7, D1)**: the private nested `ResponseMapper` owns the private nested `Response` DTO (`Response`, `Error`, `Title`, `Year`, `Runtime`, `Plot`, `imdbRating`, `imdbID`, all `string?`, `[JsonPropertyName]` where the wire name differs). Title must be present, non-blank and not `N/A`. `Plot` → synopsis, `N/A` or absent → null. `Year` → leading four digits → `ReleaseYear.TryCreate(int, DateTimeOffset now, out …)`, `now` from `TimeProvider.GetUtcNow()`. `Runtime` → the `"<n> min"` form → `Runtime.TryCreate(int, out …)`. `imdbRating` → `decimal.TryParse` with `CultureInfo.InvariantCulture` → `ImdbRating.TryCreate(decimal, out …)`. `imdbID` → `ImdbId.TryCreate(string?, out …)`. Every factory is used, so a parse *or* domain failure nulls that field alone and never fails the lookup. One private helper per field keeps the mapper under the complexity gate. It is private and nested rather than a separate top-level type, so no `InternalsVisibleTo` is needed and no vendor-named file appears.
- **Logs (Q11, D1)**: the private nested `partial Log` with `[LoggerMessage]` warnings `InvalidApiKey`, `RateLimited`, `ProviderUnavailable` (status code if any, category, exception **type name**) and `InvalidResponse` (status code or "malformed body"). No URI, key, title, provider `Error` text, raw exception message or exception object is passed in; movie and trace context is inherited from the enclosing scope and activity.
- **Telemetry (Q11, D2, [R-3])**: `Metadata.Lookup` is a child of `Activity.Current` on a source with the same name as every existing one. On `Failed`, the only tag is `TelemetryConstants.ErrorType` = the failure category name, and the activity status is set to `ActivityStatusCode.Error`. On `Found` and `NotFound` there is no outcome tag and the status is left unset. There is no HTTP status-code tag: no constant exists for one (R:140), constitution VI:229 forbids an ad-hoc literal, and the status code is already on the `System.Net.Http` child span. No title, URI or key tag. Built-in HttpClient and Polly telemetry stays at its defaults and `System.Net.Http` query redaction is never disabled.
- **Health (Q11, D3, D4, [R-2])**: `public sealed class MetadataProviderHealthState` records the last lookup's failure category, whether that outcome was a 401, and its `TimeProvider` time; the adapter writes to it. It is public only because the public adapter's primary constructor takes it — every member is `internal`, so nothing is exposed and CS0051 cannot fire. `internal sealed class MetadataProviderHealthCheck : IHealthCheck` maps it to Healthy (no lookup, Found, NotFound), Degraded (RateLimited, ProviderUnavailable, **and an `InvalidResponse` that was not a 401** — the category alone cannot tell a bad key from a malformed body, hence the separate flag), or Unhealthy with the key-configuration description (401 only). It makes no network call. Registered by `AddMetadataProvider` via `AddHealthChecks().AddCheck<MetadataProviderHealthCheck>("metadata-provider", tags: ["ready"])`, which keeps the comment invariant at `ServiceDefaults/Extensions.cs:14` — the Api adds no second `AddHealthChecks`. Tests observe it through `HealthCheckService` and `IOptions<HealthCheckServiceOptions>`, the pattern at `RabbitMqServiceCollectionExtensionsTests.cs:102`.
- **Registration (Q5, Q8, D1, [R-3])**: `public static class MetadataProviderServiceCollectionExtensions.AddMetadataProvider(this IServiceCollection)`:
  - `AddHttpClient<IMetadataProvider, OmdbMetadataProvider>((provider, client) => client.BaseAddress = new Uri(provider.GetRequiredService<IOptions<OmdbOptions>>().Value.BaseUrl))`; the `IMetadataProvider` here is always `LamuFlix.Core.Ports.IMetadataProvider`.
  - `.AddStandardResilienceHandler()` configured through the `IServiceProvider`-aware overload so the handler reads `IOptions<MetadataProviderResilienceOptions>` — tests change behaviour only through configuration, with no test-only seam.
  - Retry: `MaxRetryAttempts`, `BaseDelay`, `BackoffType = Exponential`, `UseJitter = true`, `ShouldRetryAfterHeader = true`. Attempt timeout, total timeout, and breaker failure ratio / sampling / minimum throughput / break duration likewise. The rate limiter stays at its default.
  - Retry and breaker share one `ShouldHandle` predicate: 5xx, 408, 429, `HttpRequestException`, `TimeoutRejectedException`. 401 and other 4xx are never retried. `MaxDelay` is not set and not claimed to cap `Retry-After`; a wait that runs past the total budget is cancelled by the total timeout and that outcome is `ProviderUnavailable` (Q4).
  - `services.TryAddSingleton(TimeProvider.System)` — a no-op in the Api, where `AddLamuFlixPersistence` already registers it the same way, and self-contained for hosts and tests that do not call persistence. A pre-registered fake still wins.
  - `services.AddHealthChecks().AddCheck<MetadataProviderHealthCheck>("metadata-provider", tags: ["ready"])`.
  - It does not call `AddLamuFlixOptions`: hosts already get options from `AddServiceDefaults` (`ServiceDefaults/Extensions.cs:13`).
- **`MetadataProviderResilienceOptions` (Q5, D1)**: `public sealed record MetadataProviderResilienceOptions : IValidatableObject` in `Core/Options`, `SectionName = "Omdb:Resilience"` — the type name is functional, the key stays vendor-named because the constitution permits vendor-mandated configuration keys (VIII:273-276, D1, `2ef2c04`). BCL types only. One `BindAndValidate<MetadataProviderResilienceOptions>` line in `ServiceDefaults/Extensions.cs`. It is a separate record rather than a member of `OmdbOptions` because DataAnnotations validation does not recurse into nested members, which keeps `OmdbOptions` unchanged. Members and Q4 defaults: `MaxRetryAttempts` 3, `BaseDelay` 1 s, `AttemptTimeout` 10 s, `TotalTimeout` 30 s, `FailureRatio` 0.1, `SamplingDuration` 30 s, `MinimumThroughput` 100, `BreakDuration` 5 s. `IValidatableObject` adds `AttemptTimeout ≤ TotalTimeout` and `SamplingDuration ≥ 2 × AttemptTimeout` (the standard handler's own rule), so an invalid configuration fails at startup.

### Validation ranges for the eight members (exact, cited)

Each `[Range]` mirrors the pinned library's own validation range, member by member. Microsoft Learn's `HttpRetryStrategyOptions` page shows the type inheriting `Polly.Retry.RetryStrategyOptions<HttpResponseMessage>`, and the `RangeAttribute`s live on that inherited Polly base type rather than on the `Http*` type, so the values below are read from the assemblies the pinned version actually resolves to, by reflection over `CustomAttributeData`: `Microsoft.Extensions.Http.Resilience` **10.10.0** → `Microsoft.Extensions.Resilience` **10.10.0** → `Polly.Extensions`/`Polly.RateLimiting` **8.4.2** → `Polly.Core` **8.4.2** (its nuspec pins 8.4.2). Polly's own API reference agrees on the retry range, showing `[Range(1, 2147483647)]` on `MaxRetryAttempts` at <https://www.pollydocs.org/api/Polly.Retry.RetryStrategyOptions-1.html>.

| Member | Validated by | Attribute form | Minimum | Maximum |
|---|---|---|---|---|
| `MaxRetryAttempts` | `Polly.Retry.RetryStrategyOptions<HttpResponseMessage>.MaxRetryAttempts` | `[Range(1, int.MaxValue)]` | **1** | `int.MaxValue` |
| `BaseDelay` | `Polly.Retry.RetryStrategyOptions<HttpResponseMessage>.Delay` | `[Range(typeof(TimeSpan), "00:00:00", "1.00:00:00")]` | **`00:00:00`** | **`1.00:00:00`** (1 day) |
| `AttemptTimeout` | `HttpTimeoutStrategyOptions.Timeout` (attempt-timeout stage) | `[Range(typeof(TimeSpan), "00:00:00.010", "1.00:00:00")]` | **`00:00:00.010`** (10 ms) | **`1.00:00:00`** |
| `TotalTimeout` | `HttpTimeoutStrategyOptions.Timeout` (total-request-timeout stage) | `[Range(typeof(TimeSpan), "00:00:00.010", "1.00:00:00")]` | **`00:00:00.010`** (10 ms) | **`1.00:00:00`** |
| `FailureRatio` | `Polly.CircuitBreaker.CircuitBreakerStrategyOptions<HttpResponseMessage>.FailureRatio` | `[Range(0.0, 1.0)]` | **`0.0`** | **`1.0`** |
| `SamplingDuration` | `Polly.CircuitBreaker.CircuitBreakerStrategyOptions<HttpResponseMessage>.SamplingDuration` | `[Range(typeof(TimeSpan), "00:00:00.500", "1.00:00:00")]` | **`00:00:00.500`** (500 ms) | **`1.00:00:00`** |
| `MinimumThroughput` | `Polly.CircuitBreaker.CircuitBreakerStrategyOptions<HttpResponseMessage>.MinimumThroughput` | `[Range(2, int.MaxValue)]` | **2** | `int.MaxValue` |
| `BreakDuration` | `Polly.CircuitBreaker.CircuitBreakerStrategyOptions<HttpResponseMessage>.BreakDuration` | `[Range(typeof(TimeSpan), "00:00:00.500", "1.00:00:00")]` | **`00:00:00.500`** (500 ms) | **`1.00:00:00`** |

Two consequences worth stating rather than leaving implicit:

- The brief's parenthetical "`FailureRatio` in (0, 1]" is not what the pinned library enforces: the attribute is inclusive of `0`. The plan mirrors the library, so the minimum is `0.0`. A ratio of `0` is accepted by the library and would let the breaker trip on the first handled failure, which is why the shipped default stays at the ruled `0.1` and the test configuration leaves it alone.
- Test configuration values must clear both the tabulated ranges and the cross-field rule. The chosen set — base delay 10 ms, attempt timeout 500 ms, total 3 s, sampling 1 s, minimum throughput 2, break 1 s — sits inside every range: base delay 10 ms ≥ `00:00:00`; attempt timeout 500 ms ≥ `00:00:00.010`; total 3 s and sampling 1 s ≥ `00:00:00.500`; minimum throughput 2 ≥ 2; break 1 s ≥ `00:00:00.500`. It also satisfies `SamplingDuration ≥ 2 × AttemptTimeout` exactly (1 s = 2 × 500 ms), so the short values are legal rather than merely small.

The standard pipeline the handler installs chains five stages, outermost first: rate limiter, total request timeout, retry, circuit breaker, attempt timeout (Microsoft Learn, `HttpStandardResilienceOptions` remarks and "Build resilient HTTP apps: key development patterns"). Its retry and breaker `ShouldHandle` defaults already cover 408, 429, 5xx and above, `HttpRequestException` and `TimeoutRejectedException`, which is the set this plan pins explicitly, so the explicit predicate restates the default rather than narrowing it; 401 and the other 4xx codes are outside that set and are therefore never retried.

- **Api host (Q8, Q9, D1)**: `builder.Services.AddMetadataProvider();` after `AddLamuFlixPersistence` and before `AddLamuFlixRabbitMq`, because `IsConsumerActive` is evaluated at registration time and registering after would leave the guard blind ([R-4]). `"Omdb": { "BaseUrl": "https://www.omdbapi.com/" }` in Api `appsettings.json`. A newly generated `UserSecretsId` in `LamuFlix.Api.csproj`, not the Worker or Web identity; it is an identifier, not a secret.

## Test Strategy (brief §5.3, as amended by D2, D4, D6, D7)

Every provider test runs against a real local HTTP server; there is no live OMDb call and no real key.

**Setup**: `Omdb:ApiKey` is a sentinel (`test-key-SENTINEL-7f3a`), `Omdb:BaseUrl` is the WireMock loopback URL, and `Omdb:Resilience:*` holds valid short values inside the tabulated ranges — base delay 10 ms, attempt timeout 500 ms, total 3 s, sampling 1 s, minimum throughput 2, break 1 s. Each test builds its own `ServiceCollection` with options binding plus `AddMetadataProvider`. Conventions (DEV-302 D23): `Method_Condition_Expected` names, `TestContext.Current.CancellationToken`, only `// arrange` / `// act` / `// assert` comments, no `DateTime.Now`; the existing `FixedTimeProvider` for the injectable clock. Per D7 (constitution IX:302) the repeated cases are `Theory` + `MemberData`, never repeated `Fact`s: 400/403/404 in one theory, the three Title variants in one, the four domain-invalid optional fields in one, and the range edges in one theory per options member.

| Class | Cases |

## Risks

- **Outcome classification complexity.** The Q6 table is wide. Mitigated by one private helper per status class and by the ≤ 6 refactor gate forcing the split rather than a suppression. Asserted by the status cases, which fix the request count per class.
- **Mapping complexity and culture.** Six fields with several failure modes each. Mitigated by one helper per field; the `pt-BR` case proves the invariant parse rather than trusting it.
- **Refactor-gate breadth.** The ≤ 6 gate covers all changed code, not just the two known hotspots, so an overlooked method in the adapter's flow, the health check or the registration can fail the gate late. Mitigated by running the complexity gate in Phase 8 over the changed-file set rather than over a hand-picked list.
- **`Retry-After` cannot be capped.** `MaxDelay` does not cap a generated delay, so an oversized header ends at the total timeout as `ProviderUnavailable`. The plan states this rather than claiming a cap (Q4), and the matrix proves both the honoured header and the oversized-header path.
- **Breaker test speed.** `MinimumThroughput = 2` in test configuration only; production keeps 100. Each test builds fresh pipeline state, so breaker state never leaks between tests.
- **Shared WireMock server across a class.** Request-count and ordering assertions are per class, and the class's server is reset per test; classes sharing a server are serialised in one collection.
- **Secret leakage through a surface not asserted.** Log redaction alone does not prove telemetry safety, so the secrecy case inspects captured structured state, exception `ToString()` and activity tags/names/descriptions on both the LamuFlix source and `System.Net.Http`.
- **Health check semantics drift from behaviour.** The check is passive by ruling (a live probe would spend the daily request quota and put the key on the wire), so it reports the last observed outcome, not current reachability. Stated here so a reader does not read it as a liveness probe. D4's separate was-401 flag is what keeps a malformed body from being reported as a key problem.
- **A stale `Omdb*` name surviving the rename.** The plan renames every new type, file, member and the health-check identifier, and names no test or helper type after the vendor; the sweep in the last pass of `tasks.md` is the backstop, because a leftover helper name is a constitution VIII:273-276 breach that no gate in this repo would catch. Recorded as a risk rather than as a claim that ArchitectureTests would have caught it — no such rule was verified.
- **The test's `IMovieRepository` fake is a stub, not the real repository.** `IsConsumerActive` only inspects registrations, so a private nested fake is enough (D6, R:28, R:209) and keeps the case on a plain `ServiceCollection`. The active path is asserted through the registrations the guard actually adds, including the `EnrichmentConsumer` hosted service.
- **Api consumer activation is untested in a real host.** No test boots the Api host, because that needs `Microsoft.AspNetCore.Mvc.Testing` — a new package, out of scope under Q3 — and a `public partial class Program`. The `ServiceCollection` composition test asserts the active-path registrations instead ([R-4]).
