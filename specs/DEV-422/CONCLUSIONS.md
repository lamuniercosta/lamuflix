## Q4 — TanStack Query cache update strategy, details nested-client reconciliation, and connect/reconnect recovery

**Question (Keel):**
Shall cache strategy treat each valid event as a freshness hint: immediately patch only `enrichmentStatus` for matching existing root `browseMovies` rows, then invalidate all `browseMovies` variants for authoritative metadata, membership and ordering, without fabricating missing rows? I recommend every-event invalidation because payload has no title/poster/filter fields; coalesce concurrent refetches and settle HTTP-vs-event races through invalidation rather than asserting unavailable global version ordering. Details nested `QueryClient` remains owned by its view: subscribe there to matching root browse cache changes and invalidate only `movieDetails` for that id; root hook must not create a second connection or refactor to one `QueryClient`. On every successful initial start and reconnect, invalidate root browse queries including pending rows and reconcile mounted details even if no event arrives, covering disconnect missed events. Invalid payloads ignored; no replay, synthetic sequencing, polling or recommendation caches. Cost is bounded event-driven HTTP refetch.

**Ruling (Patron):**
Approved — patch matching root `['browseMovies']` rows immediately on valid `EnrichmentStatusChanged` events and invalidate `['browseMovies']` for authoritative HTTP state, reconcile mounted `['movieDetails', movieId]` in `MovieDetailsView`'s nested client without a second connection, and invalidate/reconcile on both initial connect and reconnect.

- **Event-driven root cache patch + invalidation (`DEV-422:15`, `recon-DEV-422:47-50,110-116,120-126`, `web/src/library/libraryQueries.ts:121-135,162,259-264`)**: Ignore malformed payloads; on each valid `{ id, enrichmentStatus }` event, patch `enrichmentStatus` in place on matching existing items across root `['browseMovies']` cache entries via `setQueriesData` (never fabricating missing rows) and invalidate `['browseMovies']` so authoritative metadata, filter membership, and sort order are refetched by HTTP without synthetic sequence numbers or recommendation-cache side effects.
- **Details nested `QueryClient` reconciliation (`web/src/features/movie-details/MovieDetailsView.tsx:341-379`, `web/src/features/movie-details/movieDetailsQueries.ts:169-191`, `recon-DEV-422:39,45`)**: Keep `MovieDetailsView`'s nested `detailsClient` intact and keep a single root SignalR connection; drive `detailsClient.invalidateQueries({ queryKey: ['movieDetails', movieId] })` from root cache/recovery notifications for the mounted `movieId` across all status transitions (`Pending`, `Enriched`, `NotFound`, `Failed`) and even when `movieId` is absent from the currently cached `browseMovies` page.
- **Initial connect & reconnect convergence (`DEV-422:15`, `docs/adr/0022-signalr-enrichment-status-push.md:15`, `recon-DEV-422:50,71,124`)**: On every successful initial `start()` and every `onreconnected`, invalidate root `['browseMovies']` queries and reconcile mounted `['movieDetails', movieId]` so any transition that occurred during startup or while disconnected converges via HTTP refetch without server replay or polling.
