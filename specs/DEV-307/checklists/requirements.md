## Notes

Ten items are recorded here so they surface at review rather than being absorbed silently. **None was a gap the writer could fill.** Three were escalated to Keel as `needs decision:` (items 1-3); the other seven are recorded, not escalated. Nothing here opens Gate 1, and nothing here pre-empts Q1 or Q2.

1. **ESCALATED - the OpenAPI half of Q2 is not executable in this ticket.** Patron rejected the OpenAPI exclusion in `CONCLUSIONS.md` Q2 and required both health routes documented in the committed `openapi.json`. **That document does not exist, and the project that would hold it does not exist either.** Verified at this HEAD, not from recon: `web/` is absent from this worktree, absent from the main checkout, and has never been tracked on any branch (`git log --all -- web` is empty); `Microsoft.AspNetCore.OpenApi` is not a `PackageReference` in any project and `AddOpenApi` appears nowhere in `src/`; the API currently maps **zero** endpoints, so there is nothing to generate a document from; and `harness.yml:37-42` states the web gates are "Off until the Epic 6 scaffold ticket creates `web/`". Satisfying FR-034 therefore needs a new package, a new top-level folder, a generation step and a drift check - PRODUCT section 5 items 1 and 2, and squarely the Epic 6 scaffold ticket's job. This is the largest gap in the brief. Carried as FR-034 marked unsatisfiable rather than dropped or satisfied.

2. **ESCALATED - Q2's Degraded mapping is unreachable under the ruled readiness membership.** `CONCLUSIONS.md` Decision A untags `MetadataProviderHealthCheck` from readiness. Verified at this HEAD: `MetadataProviderHealthCheck.cs:31` is the **only** place in the readiness set that can report Degraded; `RabbitMqHealthCheck.cs:22-28` returns only Healthy or Unhealthy, and the PostgreSQL `AddDbContextCheck` the brief specifies returns only Healthy or Unhealthy. So the aggregate readiness status is **binary**, and the owner is being asked to choose between two behaviours production cannot currently reach. The brief's own test strategy (line 99) proves "200 when Degraded" only by replacing the checks with stubs - a state no production registration produces. This does not make the choice meaningless (a future check could report Degraded, and the contract is being fixed now), but it changes what the checkbox should ask, so the writer is not entitled to decide it.

3. **ESCALATED - the endpoint tests cannot boot the host today.** The brief's test strategy (line 99) and constitution.md:288 and :359-360 all require `WebApplicationFactory` tests of both routes. Verified: `tests/LamuFlix.IntegrationTests/LamuFlix.IntegrationTests.csproj:20-24` references Infrastructure, ServiceDefaults and Tests.Common but **not `LamuFlix.Api`**, so the test project cannot name `Program` at all. Delivering the tests therefore needs a `ProjectReference` to `LamuFlix.Api` and the `Microsoft.AspNetCore.Mvc.Testing` reference beside it - PRODUCT section 5 items 2 and 6, on a project file the ticket does not name. **No entry-point declaration is part of it**: recon round 8 (`recon-307-8-program-gen.md`) established that .NET 10 source-generates the `public partial class Program` for a top-level-statement project and that ASP0027 flags an explicit one as unnecessary, so the line an earlier draft of this item asked for is dropped. **The wording of the question is not held in this file: `plan.md` section 8 N2 is the single source of it**, recorded there as one combined checkbox with both halves - the first half approving the two entries in that one project file, which is charter 2.3(6) and Patron's and is the plan's default harness, and the second half being the Kestrel-in-test harness, which is a constitution departure and the user's. Neither half is folded into Q1 and the endpoint tests are not deferred.

4. **The clock is registered three times today, and this ticket changes which one decides rather than how many there are.** Verified: `PersistenceServiceCollectionExtensions.cs:31` and `MetadataProviderServiceCollectionExtensions.cs:30` each call `TryAddSingleton(TimeProvider.System)`. Scope 4 asks for the registration in the shared defaults, and because `AddServiceDefaults` runs first at `Program.cs:11`, the new registration becomes the owner and the other two become no-ops. FR-018 and FR-019 record the outcome; removing the other two would mean rewriting two files the ticket does not name, so it is not done. Recorded so a reader of the diff does not mistake the two untouched calls for an oversight.

5. **The shared defaults already depend on the application, and this ticket deepens an existing coupling rather than creating one.** constitution.md:109 says `LamuFlix.ServiceDefaults` may reference "nothing application-specific", but `LamuFlix.ServiceDefaults.csproj:12` already references `LamuFlix.Core` for the options records. FR-008 requires the activity-source name to come from the same `Core` constants holder, so the reference is used a second time. Recorded because the alternative - hardcoding "LamuFlix" in the shared defaults - is forbidden twice over (constitution.md:225-229, and the brief's frozen scope 2), and the pre-existing deviation is the scaffold epic's to retire.

6. **The RabbitMQ activity-source names are foreign names, and they still get a constant.** FR-007 collects the client's own publisher and subscriber sources. Those two strings name a third party's instrumentation, not ours, but constitution.md:225-229 bars ad-hoc literals for telemetry names, so they are held in the same constants holder. Recorded because a reader may reasonably expect vendor names to be allowed as literals, and the constitution's wording does not carve them out.

7. **Options validation is retained as-is, including a double binding.** The shared defaults already bind and validate seven records (`Extensions.cs:22-28`), and `PersistenceServiceCollectionExtensions.cs:32-36` binds `EnrichmentOptions` a second time with an extra production-only validator. `AddOptions<T>()` is additive, so both validators run. This is pre-existing, correct, and untouched. Recorded because the ticket's title names "options validation", which invites a reader to expect it to change; it does not.

8. **A validation exception that is genuinely a server fault is recorded as a client mistake.** The ticket's Decision defines the split by exception type, not by cause, so the tracing decorator cannot tell the two apart. SC-010 and US5 scenario 1 record the ticket's behaviour; the edge case names the consequence for the error-rate reading. Recorded because it is the one place this ticket knowingly degrades a signal, and the reader deserves to know it was a decision rather than an oversight.

9. **A non-fully-healthy aggregate is the one health state no test can reach without stubs.** This follows from item 2 and is recorded separately because it changes what the Q2 test task can honestly assert: a test can only prove the Degraded mapping by registering a stub check that production never registers, so such a test proves the writer's mapping, not a production behaviour. The Q2 implementation task must say which it is doing.

10. **The tracer-provider and exporter assertions are registration assertions, and that is the honest limit.** AC3 says "Telemetry exports via OTLP" and `CONCLUSIONS.md` §Recon notes that "exporter registration alone is not evidence that telemetry exports via OTLP". There is no collector in continuous integration, so SC-003 and FR-027 assert that the providers and exporters are composed, and no test claims a round trip. Recorded so the gap between the assertion and the ticket's wording is visible rather than papered over by a test name that overclaims.

**Gate lines to be run and recorded, not assumed.** The vulnerable-packages gate **is** run, because this work adds packages (FR-031, SC-012). The property gate's scope-empty result and the mutation gate are both addressed in `plan.md` §Gates, each carried as a task so neither is discovered at the gate.

No finding required a spec update after this pass, and no finding opened Gate 1. Three questions were raised to Keel and none is answered here.
