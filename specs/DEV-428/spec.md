# Feature Specification: Consume thumbnail requests and serve cached JPEGs

**Feature Branch**: `feature/428-spec`
**Created**: 2026-10-30
**Status**: gate1: provisional
**Input**: Ticket DEV-428 (parent DEV-100, Size M; depends on DEV-17; blocks tiles DEV-429); frozen `brief.md` (Q1–Q7 + Post-grill Analyze Ruling U1 + Phase 2 Step 7 Patron rulings P1–P20); `CONCLUSIONS.md`; `ASSUMPTIONS.md`; Maestri notes `DEV-428`, `recon-DEV-428`, `recon-DEV-428-2`, `adjudication-DEV-428-plan`, `adjudication-DEV-17-plan`; `specs/PRODUCT.md`; constitution Principles V and VI

## Scope

**In scope** (ticket Scope & Technical Design items 1–6 and AC 1–3; brief Q1–Q7; Phase 2 Step 7 P1–P20):

1. Durable quorum queue `thumbnail` with own DLQ `thumbnail.dead-letter` on existing RabbitMQ exchange conventions; message `ThumbnailRequested(MovieId MovieId, string FilePath)` in Core/Ports; no thumbnail retry queue; `x-single-active-consumer=true`, prefetch 1, serial handling under ordinary broker dispatch (Q1, Q4, Q5; P5).
2. Api-hosted `ThumbnailConsumer` calling DEV-17 `IThumbnailGenerator`, opt-in via `Thumbnails:Enabled` default false, with `InactiveThumbnailConsumer` when disabled; both consumer registration and endpoint read startup-validated `IOptions<ThumbnailOptions>.Value` (restart required to toggle the flag) (Q1, Q6; P11).
3. `GET /api/movies/{id:int}/thumbnail`: inherits landed `LibraryEndpoints` caller-access policy (verified at T000; no new auth subsystem); serves cached `image/jpeg` with `X-Content-Type-Options: nosniff` on 200 after canonical SOI check on stream open, or uniform sanitized 404 RFC 7807 `ProblemDetails` (identical `status`/`title`/`type`; only per-request `traceId` and optional `instance` may differ) via one `NotFoundException` → `GlobalExceptionHandler` / `AddProblemDetails` mechanism with OpenAPI `.Produces(200, image/jpeg)` + `.ProducesProblem(404)`; no generation or media-source access on GET (Q1, Q3; C2; P1, P8, P11, P12).
4. Publish only after successful enrichment persistence when thumbnails enabled, poster absent, and local source present; publisher confirmation before enrichment acknowledgement; when enabled, publish/topology failure intentionally prevents enrichment ack and redrives enrichment via its existing retry/DLQ pipeline (no new outbox/alerts); publisher injects mandatory `traceparent`/`tracestate` (Q1, Q4; C1; P4).
5. Record one sanitized failure per terminal handling attempt using closed U1 consumer tokens and/or closed DEV-17 generator tokens and the closed U1 log-field set; missing binary (`BinaryNotFound`) is permanent — terminal DLQ, no retry loop; operator runbook: disable or repair binary, restart Api, inspect/purge DLQ (Q1, Q4; U1; P6).
6. Fake-generator consumer proof and endpoint 200/`ProblemDetails` 404 proof, expanded by the brief proof matrix including Principle VI propagation/Activity proofs, U1 token/field proofs, planted symlink destination/source handoff, Windows concurrent streaming/promotion, and corrupt-`traceparent` malformed handling (Q1, Q7; C1; U1; P2, P3, P5, P9).

Concrete singleton `ThumbnailCache` registered by DEV-428 in `RabbitMqServiceCollectionExtensions` and resolved by both consumer and endpoint with `IOptions<ThumbnailOptions>`; consumer owns eligibility/source authorization via focused private helpers; cache owns containment/SOI/open/promotion; atomic promotion of DEV-17 GUID JPEG to canonical `{movieId}.jpg` with symlink/reparse rejection on temp, canonical, and ancestors; SOI-validated cache-hit skip and serve-time SOI; library-root source authorization with immediate canonicalize/revalidate at handoff; closed DEV-17 failure tokens preserved; U1 closed non-generator tokens and log fields; Principle VI publisher/consumer Activity propagation with non-throwing extract fallback; contract chain regenerated without hand-edits (Q2–Q7; C1; U1; P2–P3, P9, P13–P14).

**Out of scope** (ticket; brief Q1, Q6, Q7; Phase 2 Step 7):

- DEV-17 generator, process runner, process execution, Docker ffmpeg, shared `ThumbnailOptions` validation/registration ownership.
- DEV-429 tile rendering.
- Cache eviction, expiry, orphan sweeping, automatic disk sweeper, distributed storage/provisioning, circuit breaker, bespoke health/counters, new outbox/alerts (P4, P6, P7).
- New NuGet/npm packages; new project/top-level folder/architectural layer; new Core port interface or Infrastructure dependency in a Core handler; new outbox table; DB schema/tables; new auth subsystem; new startup filesystem write probe or custom root-restriction validator beyond landed options validation (P1, P10).
- Root glossary / `CONTEXT.md` rewrites; new ADR (consume DEV-17 ADR0033 after landing); dirty `harness.yml` edits; unrelated cleanup; production deletions or whole-file rewrites; changed gate thresholds (P16).
- Playback implementation or `Features:LocalPlay` changes; DTO/`PosterUrl` field changes; ETag/Cache-Control/Range policy; bespoke health infrastructure or custom metrics (Principle VI Activity/`TelemetryConstants` span names for this queue are required, not bespoke metrics; Q6; C1).
- Web UI work beyond regenerated OpenAPI/TypeScript contracts.
- Anything else is a follow-up issue, not a finding in this round (Q1).

## User Scenarios & Testing

### User Story 1 - Enabled generate-and-serve path (Priority: P1)

As a library operator with `Thumbnails:Enabled=true`, after enrichment of a posterless movie that has a local file, I need a cached JPEG produced and served so the UI can show a local fallback when no external poster exists.

**Why this priority**: Ticket AC 1; Scope items 1–4, 6.

**Independent Test**: Persist enrichment for an eligible movie → publisher-confirmed `thumbnail` message → fake generator → canonical JPEG → `GET` returns 200 with exact bytes, `image/jpeg`, and `X-Content-Type-Options: nosniff`.

**Acceptance Scenarios**:

1. **Given** `Thumbnails:Enabled=true` and a movie with no poster and a local path **When** enrichment persistence succeeds **Then** a publisher-confirmed `ThumbnailRequested` is published before enrichment acknowledgement, with mandatory `traceparent`/`tracestate` injected via `TraceContextCarrier` / `Propagators.DefaultTextMapPropagator` and a producer Activity whose name lives in `TelemetryConstants` (Q4; C1; Principle VI).
2. **Given** an eligible `ThumbnailRequested` **When** the consumer handles it with a fake generator that writes a SOI-valid JPEG **Then** the consumer extracts propagation headers (non-throwing fallback), starts a consumer Activity (redelivery uses `ActivityLink`), immediately canonicalizes/revalidates the authoritative source under `LibraryOptions.RootPath`, containment-checks (including ancestor symlink/reparse rejection) and atomically promotes the output to `{movieId}.jpg` under `CacheDirectory`, and acknowledges the message (Q2, Q5; C1; P2, P3, P9).
3. **Given** that canonical JPEG exists and passes serve-time SOI **When** `GET /api/movies/{id:int}/thumbnail` is called **Then** the response is `200 OK` with `Content-Type: image/jpeg`, `X-Content-Type-Options: nosniff`, and the exact cached bytes, streamed asynchronously with per-request disposal and `FileShare.ReadWrite | FileShare.Delete` (Q3, Q7; P5, P8).
4. **Given** a duplicate delivery and a readable canonical JPEG with length ≥ 2 and SOI `0xFF 0xD8` **When** the consumer handles it **Then** generation is skipped and the message is acknowledged (Q5).

### User Story 2 - Disabled short-circuit (Priority: P1)

As an operator with thumbnails off (the default), I need zero thumbnail publication, subscription, generation, source checks, or cache I/O, and the endpoint must return 404 even if a JPEG already exists on disk. Toggling `Thumbnails:Enabled` requires an Api host restart (startup `IOptions<ThumbnailOptions>.Value` snapshot; no hot-reload asymmetry).

**Why this priority**: Ticket AC 2; Q6; P11.

**Independent Test**: Flag off — no publication/subscription/generation/source validation/cache I/O; GET returns uniform sanitized 404 RFC 7807 `ProblemDetails` with `traceId` even when a cached JPEG exists; HTTP remains available when broker is disabled.

**Acceptance Scenarios**:

1. **Given** `Thumbnails:Enabled=false` (default) **When** the host starts **Then** `InactiveThumbnailConsumer` is registered from the startup-validated `IOptions<ThumbnailOptions>.Value` snapshot and no active thumbnail subscription or publication occurs (Q4, Q6; P11).
2. **Given** the flag off and a JPEG already on disk **When** `GET /api/movies/{id:int}/thumbnail` is called **Then** the response is uniform sanitized `404 Not Found` as RFC 7807 `ProblemDetails` (`status: 404`, identical `title`/`type` across miss classes; `traceId` present; optional `instance` may vary; zero path or miss-reason detail) via the single `NotFoundException` → `GlobalExceptionHandler` path before any cache I/O, generator call, or source-path check — never a bare empty 404 body and never a competing miss mechanism (Q6; C2; Principle V; P1, P12).
3. **Given** the flag off **When** enrichment completes for an otherwise eligible movie **Then** no `ThumbnailRequested` is published (Q4, Q6).
4. **Given** an operator changes `Thumbnails:Enabled` **When** the change must take effect **Then** an Api host restart is required (P11).

### User Story 3 - Source and cache trust boundaries (Priority: P1)

As a maintainer, I need the consumer to revalidate the authoritative movie and authorize the source beneath `LibraryOptions.RootPath` immediately before generation, and to promote only contained generator outputs that are not symlink/reparse escapes, so broker paths and escaped paths cannot drive generation or destroy unrelated cache files. Residual name-based TOCTOU under trusted operator-owned directories is documented, not claimed eliminated.

**Why this priority**: Q3; DEV-428 ownership of library-root authorization (recon-DEV-428-2); P2, P3.

**Independent Test**: Outside-root, traversal, sibling-prefix, symlink/reparse escape (file and ancestors), planted canonical symlink destination, and stale broker path rejected; output outside cache rejected without deleting unrelated files; failed promotion preserves prior regular canonical JPEG and leaves outside targets untouched; immediate handoff revalidation proof; do not assert races are impossible.

**Acceptance Scenarios**:

1. **Given** a `ThumbnailRequested` for a nonexistent movie, a movie that now has a poster, a movie without local path, or a `FilePath` differing from the current authoritative `Path` **When** the consumer handles it **Then** the request is terminally rejected without calling the generator and one sanitized failure is logged with `FailureReason` `IneligibleRequest` under the closed U1 field set (Q3; U1).
2. **Given** a source that escapes `LibraryOptions.RootPath` via traversal, sibling-prefix, or symlink/reparse on the file or its ancestor chain **When** authorization runs (canonicalize/revalidate immediately before `GenerateAsync`) **Then** generation is not invoked, the attempt is terminal, and the logged token is `UnauthorizedSourcePath` (Q3; U1; P3).
3. **Given** a successful `ThumbnailResult` whose `CachePath` does not resolve directly beneath `CacheDirectory`, or whose temp/canonical/ancestor path is a symlink/reparse point **When** promotion is attempted **Then** the path is rejected without deleting unrelated files, any outside target remains untouched, any prior valid regular canonical JPEG is preserved, and the logged token is `CachePromotionFailed` (Q2, Q3, Q7; U1; P2).
4. **Given** an existing valid regular canonical JPEG and a failed promotion (including a planted symlink at `{movieId}.jpg`) **When** promotion fails **Then** the prior regular canonical JPEG is preserved (or the planted link is rejected without following it), only the consumer’s own contained temporary output is cleaned, outside targets are untouched, and the logged token is `CachePromotionFailed` (Q2; U1; P2).
5. **Given** an unreadable or SOI-invalid canonical file **When** a duplicate arrives **Then** generation runs and the file is atomically replaced rather than silently acknowledged (Q5; P8).
6. **Given** the DEV-17 string `sourcePath` contract **Then** residual name-based TOCTOU under trusted operator-owned `LibraryOptions.RootPath` / `ThumbnailOptions.CacheDirectory` is accepted and documented; no handle-based generator redesign and no claim that all races are impossible (P3).

### User Story 4 - Terminal failures without retry loops (Priority: P1)

As an operator, when ffmpeg is missing or generation/promotion fails, I need one sanitized structured failure for that handling attempt and a terminal DLQ entry with no thumbnail retry queue or automatic redrive, plus a documented disable-or-repair / restart / DLQ inspect-purge runbook.

**Why this priority**: Ticket AC 3; Scope item 5; Q4; P6.

**Independent Test**: All closed generator failure tokens; all four U1 consumer tokens; closed U1 log fields only; `BinaryNotFound` yields one sanitized terminal failure and DLQ entry with no retry loop; zero raw paths/payload/process output; host shutdown cancellation requeues with best-effort own-contained-temp cleanup and without generator-failure logging; malformed body plus corrupt-`traceparent` still terminal `MalformedMessage`; error Activity events carry movie-id context where the request was parsed.

**Acceptance Scenarios**:

1. **Given** a failed `ThumbnailResult` with `FailureReason` `BinaryNotFound` **When** the consumer finishes the attempt **Then** exactly one sanitized structured failure is logged using closed fields `{MovieId}`, `{FailureReason}`, `{Redelivered}` (and `{ErrorType}` only for unexpected exceptions), the message is rejected without requeue to `thumbnail.dead-letter`, and no retry loop starts; operator runbook is disable `Thumbnails:Enabled=false` (or install `ffmpeg` at `FfmpegPath`), restart Api, inspect/purge `thumbnail.dead-letter` via standard RabbitMQ management tooling (Q4; recon-DEV-428-2 closed tokens; U1; P6).
2. **Given** any other closed generator failure token (`Disabled`, `InvalidSourcePath`, `ProcessTimedOut`, `ProbeFailed`, `NoVideoStream`, `InvalidDuration`, `ExtractionFailed`, `InvalidOutput`, `StorageError`) **When** handled **Then** one sanitized failure for that attempt records the exact generator token under the closed U1 field set and the message is terminally dead-lettered without requeue (Q4, Q7; U1).
3. **Given** a malformed/invalid message body and/or corrupt `traceparent`/`tracestate` headers **When** handled **Then** non-throwing extract fallback preserves terminal contract: `FailureReason` is `MalformedMessage`, `{MovieId}` is omitted because deserialization failed, `{Redelivered}` is present, and the message is terminally dead-lettered; no raw payload is logged; corrupt headers never throw out of the consumer loop or bypass DLQ (U1; Q4; P9).
4. **Given** host shutdown cancellation (`stoppingToken.IsCancellationRequested`) interrupting after `GenerateAsync` returns a path **When** handling is interrupted **Then** best-effort cleanup deletes only that attempt’s own contained temporary `<guid:N>.jpg` before requeue, and no generator-failure log is emitted (Q4; P7).
5. **Given** at-least-once delivery **Then** no cross-crash deduplication or exactly-once guarantee is claimed; enrichment redelivery may duplicate publication; consumer redelivery starts the process Activity with an `ActivityLink` to the extracted parent context (Q4; C1).
6. **Given** a terminal processing error after a parsed request **When** the Activity is marked failed **Then** error tags include `TelemetryConstants.MovieId` and `TelemetryConstants.ErrorType` (exception type name only) with no path-bearing exception object logged (C1; U1; Principle VI).

### User Story 5 - Concurrency, composition, and contract chain (Priority: P2)

As implementers, I need broker-enforced single-active consumption under ordinary dispatch (rare overlapping generation is benign last-writer-wins), independent Windows-safe HTTP reads during generation/promotion, inactive/enabled composition without `Features:LocalPlay` coupling, singleton cache DI, and a regenerated C# → OpenAPI → TypeScript contract for the new route.

**Why this priority**: Q5–Q7; enables Size M verification and review; P5, P14.

**Independent Test**: Queue arguments, prefetch, serial processing; second consumer cannot become concurrently active under ordinary broker dispatch (no claim across failover/partition); independent asynchronous HTTP reads with `FileShare.ReadWrite | FileShare.Delete` while promotion proceeds on the target platform; inactive variant and existing global broker gating; GET remains available when broker is disabled; OpenAPI/TS regeneration and drift checks; no LocalPlay coupling.

**Acceptance Scenarios**:

1. **Given** queue `thumbnail` declared with `x-single-active-consumer=true`, consumer `prefetchCount=1`, and serial handling **When** multiple Api replicas exist **Then** only one active consumer processes thumbnail messages under ordinary broker dispatch; rare overlapping generation across failover/partition is benign last-writer-wins on deterministic `{movieId}.jpg` (Q5; P5).
2. **Given** generation/promotion in progress **When** concurrent `GET` requests arrive on the target platform **Then** each streams the canonical file asynchronously with per-request disposal, `FileShare.ReadWrite | FileShare.Delete` (+ `FileOptions.Asynchronous`), and no shared generation lock or unbounded retry loop (Q2, Q5; P5).
3. **Given** `Thumbnails:Enabled=true` **When** composition runs **Then** active subscription also respects existing broker activation rules; GET serves cache independently of broker state; the same singleton `ThumbnailCache` and `IOptions<ThumbnailOptions>` are resolved by consumer and endpoint (Q6; P14).
4. **Given** the new route **When** contracts are regenerated through repository tooling **Then** `web/src/api/openapi.json` and `web/src/api/types.ts` update without hand-edits; OpenAPI documents success `image/jpeg` (`.Produces(200, "image/jpeg")`) and error `ProblemDetails` 404 (`.ProducesProblem(404)`); no web UI work (Q3, Q7; C2; P12).
5. **Given** verification and Size M review **Then** required gates and three-axis reports run under the brief closing bar (Q7).
6. **Given** GET miss classes (disabled, nonpositive/unknown numeric id, missing/unreadable/corrupt-SOI cache) **When** asserted in tests **Then** each returns the same uniform sanitized RFC 7807 `ProblemDetails` at status 404 with `traceId` present (`application/problem+json`), zero path/miss-reason detail, never bare `Results.NotFound()` empty bodies, via the single landed miss mechanism (C2; Principle V; P1, P8, P11, P12).

### Edge Cases

- Poster-present or no-local-source movies publish nothing; consumer revalidates current eligibility (Q4, Q7).
- GET never generates or opens source media; disabled, nonpositive/unknown numeric id, or missing/unreadable/corrupt-SOI cache return uniform sanitized 404 `ProblemDetails` with `traceId` (Q3; C2; P1, P8, P11).
- Broker paths are not authorization; trust only operator-configured cache/tool/root options (Q3).
- Supported default is one Api instance with persistent operator-controlled cache and library directories; multi-instance requires operator-shared backing storage — no distributed availability guarantee (Q6).
- Crash-interrupted temp files need no background sweeper; operators monitor `CacheDirectory` disk usage and manually purge while host is stopped (or with `Thumbnails:Enabled=false` after restart); shutdown best-effort cleans only own contained temp before requeue (Q6; P7).
- When `Thumbnails:Enabled=true`, thumbnail publish/topology failure intentionally couples to enrichment non-ack and existing enrichment retry/DLQ redrive; no new outbox (P4).
- Residual name-based TOCTOU under trusted operator directories is accepted; races are not claimed impossible (P3).
- Terminal failure logs never include raw `FilePath`, `CachePath`, `RootPath`, `CacheDirectory`, payload bodies, path-bearing exception text, stdout, or stderr (U1).
- Anything outside frozen scope is a follow-up issue, not a finding in this round (Q1).

## Requirements

Set `x-single-active-consumer=true` on `thumbnail`. Routing keys follow existing Features-style convention where the routing key matches the queue name (`thumbnail`, `thumbnail.dead-letter`). Consumer channel uses `prefetchCount=1` and serial message handling. SAC + prefetch bound ordinary broker dispatch only; do not claim prevention of brief concurrent activation across failover or network partitions — rare overlapping generation is benign last-writer-wins on deterministic `{movieId}.jpg` (Q1, Q4, Q5; recon-DEV-428:20-25; P5).
- **FR-002**: Add Core message record `ThumbnailRequested(MovieId MovieId, string FilePath)` in `src/LamuFlix.Core/Ports/ThumbnailRequested.cs`. Do not add a new Core port interface, outbox table, or Core queue abstraction (Q1, Q4, Q7).
- **FR-003**: Implement concrete `RabbitMqThumbnailQueuePublisher` in Infrastructure/RabbitMq. From `EnrichmentConsumer`, after successful enrichment persistence and before enrichment `BasicAckAsync`, publish only when `Thumbnails:Enabled=true`, authoritative movie has absent `PosterUrl`, and a local `Path` is present. Require publisher confirmation before enrichment acknowledgement. When enabled, thumbnail topology or publish failure MUST NOT acknowledge enrichment and intentionally redrives enrichment via its existing retry/DLQ pipeline; add no new outbox table, Core port, or bespoke alerting/metrics. No Infrastructure reference from a Core handler. Publisher MUST start a producer Activity whose span name is a `const` in existing `TelemetryConstants` (no ad-hoc literals), tag `TelemetryConstants.MovieId`, and inject mandatory `traceparent`/`tracestate` into message headers via `TraceContextCarrier.Inject` / `Propagators.DefaultTextMapPropagator` (Q4, Q7; C1; Principle VI; Features/Enrichment publisher pattern; P4).
- **FR-004**: Implement `ThumbnailConsumer` and `InactiveThumbnailConsumer` in Infrastructure/RabbitMq, hosted by Api. Gate by `Thumbnails:Enabled` (default false) read from startup-validated `IOptions<ThumbnailOptions>.Value` (not mixed with `IOptionsMonitor` hot-reload); toggling the flag requires Api host restart. When disabled, register the inactive variant and perform no active thumbnail subscription or publication. When enabled, active subscription also obeys existing RabbitMQ consumer activation rules. Register independently of `Features:LocalPlay`. Add no bespoke thumbnail health-check infrastructure or custom metrics. Active consumer MUST extract `traceparent`/`tracestate` via a non-throwing fallback (corrupt/malformed headers never throw out of the consumer loop or bypass terminal `MalformedMessage` + `BasicRejectAsync(requeue: false)`), start a consumer Activity (span name from `TelemetryConstants`), use an `ActivityLink` on redelivery, and tag `TelemetryConstants.MovieId` plus `TelemetryConstants.MessagingDeliveryCount`; error Activity events MUST carry movie-id context and `TelemetryConstants.ErrorType` (exception type name only). Movie eligibility and `LibraryOptions.RootPath` authorization live as focused private helpers inside `ThumbnailConsumer` (harness cyclomatic thresholds apply); introduce no new class/interface/service layer (Q1, Q6, Q7; C1; Principle VI; P9, P11, P13).
- **FR-005**: Consumer loads the authoritative movie by id; terminally rejects nonexistent/stale/ineligible requests (poster now present, absent local path, queued `FilePath` ≠ current `Path`) with U1 token `IneligibleRequest`. Immediately before `IThumbnailGenerator.GenerateAsync`, canonicalize and revalidate the authoritative source beneath operator-configured `LibraryOptions.RootPath` with separator-aware OS comparison; reject traversal, sibling-prefix, and symlink/reparse escapes on the file and its ancestor chain with U1 token `UnauthorizedSourcePath`. Never trust broker paths as authorization. Residual name-based TOCTOU under trusted operator-owned directories is documented and accepted; retain the DEV-17 string `sourcePath` contract; do not claim races are impossible (Q3; U1; P3).
- **FR-006**: Call DEV-17 `IThumbnailGenerator.GenerateAsync(string sourcePath, CancellationToken cancellationToken = default)` unchanged; consume `ThumbnailResult(bool Success, string? CachePath, string? FailureReason)` and its closed failure tokens and cancellation behaviour. On `Success == false`, log the exact closed generator `FailureReason` token. Do not leak raw exception/path/process output. Do not duplicate DEV-17 process/Docker ownership (Q2; recon-DEV-428-2; U1).
- **FR-007**: Implement concrete `ThumbnailCache` in `Infrastructure/Thumbnails/ThumbnailCache.cs` for canonical path `{movieId}.jpg`, containment checks, SOI checks (`Length >= 2`, starts `0xFF 0xD8`), file reads, and atomic promotion from validated generator GUID JPEG under trusted `CacheDirectory`. Reject symlink/reparse points (`FileAttributes.ReparsePoint` / `LinkTarget != null`) on the generator temp `<guid:N>.jpg`, the canonical `{movieId}.jpg`, and their ancestor chain under `CacheDirectory`; same-directory replacement MUST NOT follow a pre-planted symlink/reparse at `{movieId}.jpg` — outside targets remain untouched and any prior valid regular canonical JPEG is preserved (rejecting a planted link is sufficient; replacing the link itself is not mandatory). Verify SOI before atomic promotion (non-SOI generator output → `CachePromotionFailed`) and when opening the canonical file for GET (corrupt/non-SOI → unreadable miss → 404). Open read streams with `FileShare.ReadWrite | FileShare.Delete` and `FileOptions.Asynchronous`; no shared generation lock or unbounded retry. Do not hardcode an unverified OS/BCL move primitive — T000/T002 verify the landed .NET 10 target-platform replacement behaviour. Promotion failure preserves an existing regular canonical JPEG, cleans only the consumer’s own contained temporary output, and surfaces U1 token `CachePromotionFailed` to the consumer log path. Duplicate deliveries may skip generation only for a readable SOI-valid canonical JPEG; otherwise regenerate. Containment, SOI, stream open, and promotion live inside `ThumbnailCache` only (Q2, Q5, Q7; U1; P2, P5, P8, P13).
- **FR-008**: Acknowledge after canonical promotion or eligible validated cache hit. On malformed/invalid message (`MalformedMessage`), terminal validation failure (`IneligibleRequest` / `UnauthorizedSourcePath`), any failed `ThumbnailResult` (exact generator token, including `BinaryNotFound`), or promotion failure (`CachePromotionFailed`): log exactly one sanitized structured failure for that handling attempt and terminal reject without requeue to `thumbnail.dead-letter`. Terminal failure log fields are closed to `{MovieId}` (omitted only for `MalformedMessage` when deserialization failed), `{FailureReason}`, `{Redelivered}`, and `{ErrorType}` (`exception.GetType().Name` only for unexpected exceptions, matching `FeaturesConsumer` without logging the raw `Exception` object when it could carry paths). Never log raw `FilePath`, `CachePath`, `RootPath`, `CacheDirectory`, payload bodies, path-bearing exception text, stdout, or stderr. No thumbnail retry queue or automatic DLQ redrive. Host shutdown cancellation requeues without generator-failure logging; when interruption occurs after `GenerateAsync` returns a path, best-effort cleanup deletes only that attempt’s own contained temporary `<guid:N>.jpg` before requeue. Follow existing broker reconnection behaviour. Document at-least-once delivery with no cross-crash failure deduplication. Operator ops: (a) `BinaryNotFound` → disable `Thumbnails:Enabled=false` or install `ffmpeg` at `FfmpegPath`, restart Api, inspect/purge `thumbnail.dead-letter` via standard RabbitMQ management tooling; (b) monitor `CacheDirectory` disk usage and manually purge while host is stopped or disabled after restart — no automatic eviction/sweeper (Q4; U1; brief Post-grill Analyze Ruling U1; P4, P6, P7).
- **FR-009**: Add `GET /api/movies/{id:int}/thumbnail` in `ThumbnailEndpoints` mapped from `ApiEndpoints`, matching `LibraryEndpoints` `{id:int}` precedent. Inherit the landed `LibraryEndpoints` caller-access policy verified at T000 — no new authentication/authorization subsystem. Read `IOptions<ThumbnailOptions>.Value` (startup-validated snapshot; flag toggle requires restart). Check `Thumbnails:Enabled` before any cache I/O; check movie existence; nonpositive (`id <= 0`) and unknown numeric ids are uniform sanitized misses. Stream only the canonical file as `image/jpeg` after serve-time SOI verification on stream open, with asynchronous per-request disposed streaming, `FileShare.ReadWrite | FileShare.Delete`, and response header `X-Content-Type-Options: nosniff` on 200 (two-byte SOI is a bounded signature check, not a full decoder; no image-decoder dependency). On miss (disabled, nonpositive/unknown id, missing/unreadable/corrupt-SOI cache) return **404** as uniform sanitized RFC 7807 `ProblemDetails` (`status: 404`, identical `title`/`type` across miss classes; zero path or miss-reason detail; only per-request `traceId` and optional `instance` may vary — byte-identical bodies across distinct requests are rejected) produced through one mechanism only: throw the existing `NotFoundException` mapped by the single `GlobalExceptionHandler` + `AddProblemDetails()` pipeline (verified at T000 against landed `LibraryEndpoints` conventions; if `NotFoundException` differs on main, use the single landed endpoint 404 `ProblemDetails` helper uniformly — never two mechanisms; never bare `Results.NotFound()` / empty 404 bodies; remove competing optional miss mechanisms). Preserve decided 404 status — do not change miss status to 422/403/500. Declare `.Produces(StatusCodes.Status200OK, contentType: "image/jpeg")` and `.ProducesProblem(StatusCodes.Status404NotFound)`.
